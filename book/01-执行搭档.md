# 第 1 章：Codex 不只是聊天窗口

“它已经把保存功能写好了。”你看到这句话时，可能会自然地松一口气。但先停一秒：你究竟看到了一个承诺、一段代码，还是一项已经运行的功能？这三者在聊天里很容易挨在一起，实际却需要不同的证据。

本章先不修改程序。我们用 LinkShelf 案例做一次只读探索，最后得到一份能指向实际文件的说明。完成后，你应能看着一次 Codex 工作过程，分别指出它**说了什么、查了什么、改了什么，以及还有什么没有验证**。如果尚未安装 Codex，可以先读到练习指令，再按[第 2 章](./02-工作环境.md)完成准备后回来操作。

## 从一句回复，看见执行循环

模型（model）根据当前信息生成下一步内容。Agent（智能体）则在执行环境中围绕任务使用工具、接收反馈，并继续作出行动选择。这里的“工具”可以是读取文件、运行终端命令、修改代码，也可能是浏览器。运行这些工具的外围系统通常称为 harness；它负责把会话、工具和权限等组织起来。不同入口所提供的工具并不完全相同。[OpenAI 的 Codex 执行架构说明](https://developers.openai.com/blog/codex-as-a-platform)解释了这一关系。

你给出的目标不会直接变成电脑里可用的软件。中间会经过一连串动作：读取已有内容，选择修改位置，写入文件，运行检查，根据结果调整。某一步失败之后，模型也可能作出错误判断。因此，“让它自主完成”仍然需要一个可检查的终点。

![从任务意图、事实调查到执行、验证和调整的工作循环](./public/diagrams/agent-loop.svg)

图中最值得注意的是反馈回路。执行得到的结果会改变下一步：文件不存在，就先找目录；测试失败，就查看失败指向什么；关键行为已通过，就交付。它不是一条“指令越长、结果越好”的直线。

## 先把四类东西分开看

一次会话里，先留意以下区别。

| 你看到的东西 | 能说明什么 | 还不能说明什么 |
| --- | --- | --- |
| “我准备检查保存逻辑” | Codex 表达了行动意图 | 它已经读过代码 |
| 读取文件的工具返回 | 某些文件内容进入了当前上下文 | 解释一定准确 |
| 修改记录或文件差异 | 指定文件确实发生了变化 | 新行为已经可用 |
| 测试或手工操作结果 | 指定条件下出现了某个结果 | 所有条件都成立 |

工具返回也不是绝对真理。例如，命令在错误目录运行，会忠实报告那个目录的情况；一个测试通过，只覆盖它设计的那条路径。证据的价值来自它与当前问题的关系。你要检查的是“这次观察支持哪个结论”，而不是“有没有出现绿色的通过字样”。

## 做一次不会改文件的项目探索

前置条件是已经下载教材源码，并能在 Codex 中打开教材根目录。CLI 用户按第 2 章进入该目录后启动；App 或 IDE 用户选择同一目录。先用文件管理器确认能看到 `cases/A-linkshelf/solution/`，里面应有网页与脚本。我们的调查对象是这份参考成品，练习起点 `starter` 则留到第 3 章使用。

以下内容发给 **Codex 输入框**，不是在操作系统终端逐行执行：

```text
请只读调查 cases/A-linkshelf/solution，不修改或新建文件，
不安装依赖，不启动长期运行的服务。
我想知道它怎样把一条链接从输入框保存到刷新后的页面。
请先确认当前目录，再读取必要文件，说明：
1. 页面入口、界面样式和行为脚本分别在哪里；
2. 新增链接时经过哪些处理，刷新后从哪里读取数据；
3. 哪些结论能引用文件中的代码，哪些需要运行后才能确认。
最后给我一条下一步验证动作，并列出实际执行的检查。
```

这段任务先限定行动范围，再给调查问题与期望产物。限制只读是因为此刻我们缺的是理解，修改会让调查对象同时变化。“读取必要文件”给它选择空间，不要求把整个仓库塞进上下文。最后要求区分代码事实与运行结果，是为了避免它读到存储调用就宣布刷新已通过。

你可能看见它列目录、读取 HTML、再定位脚本中的函数；也可能直接按文件名读取。动作顺序不同没有关系。先观察工具记录，找出它究竟读取了哪些路径。如果当前入口没有文件工具，它可能只能讨论你粘贴的内容。这时应记录“尚未直接调查本地文件”，并按第 2 章连接正确工作区。

## 怎样检查这份说明

不要只读最后的总结。打开实际文件，挑一条关键结论核对：例如“刷新时从浏览器存储加载数据”。在脚本中寻找它引用的存储键或读取调用，再向前看这段代码何时执行。不会读代码也可以要求 Codex 展示前后几行并用普通话解释，重点是让解释有可定位的对象。

接着比较“读取到代码”和“观察到功能”。假设脚本里存在 `localStorage.setItem`，这支持“实现尝试写入浏览器存储”；它不直接证明每次保存都成功。存储可能被浏览器限制，调用也可能没有经过当前按钮触发。是否能保存，仍需要新增并刷新。这个检查会在第 3 章完成。

最后检查变化范围。这个任务正确的交付是调查结论，教材文件应保持原样。若使用的界面有变更列表，查看是否出现新增或修改。已会 Git 的读者可比较任务前后的 `git status --short`；尚未学习 Git 的读者可以让 Codex说明是否写入文件，并在文件管理器中核查。仅凭它说“我没有修改”仍然是一份声明，变化列表能提供更直接的依据。

可以用下面的文字追问，继续发给 Codex：

```text
请从刚才的说明中选出一条最重要的结论，
引用它对应的真实文件与代码片段。
再指出一条你没有运行验证、因此不能直接宣布通过的结论。
```

完成时，你应该能自己写出四句话：它表达了什么判断；实际读取了哪些文件；是否有文件变化；下次怎样检查刷新保存。无需写成正式报告，四句话已足够让你的判断落在事实之上。

## 当过程与预期不同时

如果它一开始就提议重构页面，说明当前执行偏离了调查目标。此时发出具体纠正：“先停止修改。当前任务只需要解释现有保存路径，请回到已读取的文件并指出证据。”如果已经发生修改，先查看改动范围，保留原有用户修改，按界面的差异确认只撤销这次误改；不要直接清空整个目录。

如果它回答得很流畅，却没有工具记录，也没有文件引用，先问它依据什么作答。它可能使用了已有上下文，也可能只做了推测。缺少日志不能自动证明它在编造，但你仍需要能追溯的文件依据。反过来，看到很多命令也不等于工作有效：十次列目录如果没有接近保存路径，就应缩小问题。

还有一种常见结果是权限拒绝。它说明某个动作没有获准，不能被写成“这个项目没有文件”。记录被拒绝的动作、目标路径与错误，再判断是否选错工作位置。权限与文件是否存在，是两个不同的问题。

## 动手练习：给结论补上证据

沿用这次调查，在自己的笔记里改写以下三句话，使每句都符合目前掌握的证据：

1. “程序有保存功能，所以数据不会丢。”
2. “Codex 说它看完了，因此已经了解全部项目。”
3. “工具报错，说明代码坏了。”
