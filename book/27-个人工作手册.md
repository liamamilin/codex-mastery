# 第 27 章：把一次成功变成下一次更容易成功

修好一次刷新故障后，你可能很想把整个过程写成永久规则：“所有任务先查存储，再运行三轮测试，再请两个 Agent 审阅。”下一次任务只是整理一份文本，这套规则却仍然要求一切照做。经验保存下来了，判断反而消失了。

本章要留下的是适用条件和有效动作。完成后，你会有一份短个人手册，知道一项方法应该放在任务说明、项目指引、Skill、脚本还是自动化里，也知道什么时候直接不保存。

## 先找到成功中真正可以迁移的部分

Phantom Delete 的可迁移经验，并不是“删除问题都要加一次保存”。它是先记录复现，再比较当前状态与重新读取的状态，选择能区分假设的检查。换成 CSV 汇总、命令行筛选或会议整理，具体检查会改变，“结论要有对应证据”仍然成立。

同样，LinkShelf 使用原生页面与本地存储，是这个小型离线案例的合适选择，不能据此推导所有项目都不该有数据库。整理经验时先问：这条做法依赖哪些条件？改变条件后，它仍然有用吗？

先用一次真实任务验证答案。若只是模型提出的建议，还没有被你试过，保留为待试方法，不急着升级成稳定规则。一次偶然成功也不必立即推广；下一次使用时观察它是否减少了重复调查或漏验。

## 按用途选择保存位置

不同位置解决不同问题，不能只因为名字更高级就迁移过去。

| 位置 | 适合留下什么 | 何时不必用 |
| --- | --- | --- |
| 当前任务说明 | 本轮目标、材料、完成状态与临时限制 | 不要把临时要求写成全局永久规则 |
| 项目指引 | 多轮都成立的启动、数据边界和检查约定 | 只发生一次、很快过期的状态应另存 |
| Skill | 重复出现、需要判断与资源配合的任务方法 | 一条命令已足够时不必封装一套流程 |
| 脚本 | 输入输出明确、值得重复执行的确定性步骤 | 含义尚未稳定时先探索，不急着自动运行 |
| 自动化 | 已可重复执行、还需要按时间或事件触发的工作 | 未验证的步骤不因定时就更可靠 |

同一方法可以有几个配合部分。例如项目指引说清运行方式，脚本负责确定性计算，Skill 说明何时使用和怎样解释结果。它们不需要各复制一份完整规则。保留一个明确来源，比五个逐渐不一致的副本更容易维护。

自动化还涉及触发频率、输入来源、失败处理与授权。只有你确实需要定期发生，才值得增加这一层。不要把“以后可能复用”写成已经创建后台任务；文本笔记不会自己调度，也不能授予外部服务权限。

## 从具体任务提炼一项方法

以案例 E2 的文本工具为例。刚接手时，判断段落边界需要读报告、看输入、解释预期；这部分仍有不确定性。确定规则后，统计与回归可以由 Python 程序重复执行。将“每次分析前重新讨论所有空白含义”保留为手工流程，反而会增加漂移。

可以请 Codex 做一次有限整理，发送到 **Codex 输入框**：

```text
请根据我们实际完成的任务，提炼三条值得复用的方法。
每条注明适用条件、最小动作、证明有帮助的观察，以及不适用情形。
只把稳定项目事实放进项目指引，当前状态留在接续记录。
先指出哪些重复步骤适合脚本；没有实际复用价值的建议不要封装。
不要自动创建定时任务、连接外部服务或修改全局配置。
```

返回结果还需要你判断。若它建议把每次聊天都自动上传为材料，先看这是否属于你的目标和授权。若它只是给每个步骤换一个术语，没有减少任何重复工作，就可以删掉。

## 写一份足够短的个人手册

在自己的笔记或专用目录保存 `my-codex-manual.md`。这个文件名没有特殊产品能力，只有在你阅读或明确提供时才参与工作。不要为了试写个人习惯，直接改变教材根目录的 `AGENTS.md`。

下面是一份**可改写示例**：

```markdown
# 我的 Codex 工作手册

- 陌生材料先定位入口与目标对象；不把别的版本当成当前事实。
- 目标模糊时，用小尝试比较方向；确定方向后才扩大实现。
- 小任务直接推进，重要取舍与必要授权向我说明具体影响。
- 修改后按目标行为检查，记录实际命令与未覆盖条件。
- 连续尝试没有新证据时，停止重复补丁，重新检查假设。
- 中断前留下当前产物、可信基准、缺口与下一项动作。
- 方法值得复用时再固化；失效规则直接删改。
```

它保留判断，没有规定每次必须分几步、用几个 Agent、跑几轮检查。你可以加入一条自己真实需要的偏好，例如“解释命令前先说明运行目录”，并观察它是否帮助下一次协作。

个人偏好也不应压过具体项目要求。若某项目有必要的测试或数据约束，要在该项目中遵守；“我习惯快速做”不能成为跳过已知关键验收的理由。手册帮助你开始判断，不代替当前事实。

## 用第二次任务检验手册

手册写得流畅，不等于有效。选一项规模适中的新任务，比较它有没有帮助你更快找到起点、减少遗漏，或在偏离时给出下一项检查。不要只问 Codex“这份手册是不是最佳实践”，它的赞同不能证明使用价值。

可以给每次实际复用留一句结果：“先核对版本，发现测试导入了参考答案，避免了错误交付。”这条观察支持保留版本核对；“加入七条格式规则后，每次都花很多时间修措辞”则提示规则可能不划算。没有进行对照计时时，不必写节省了多少分钟。

当某条规则反复需要例外，先检查它是否过宽。把“所有任务先制定计划”改为“关键路线未知且会影响大量工作时，先安排一项探索或小实验”，常比追加越来越长的例外条款清楚。

## 删除也是维护

项目一旦更换技术，旧启动命令可能失效；临时权限恢复后，绕行步骤也可能不再需要。保留失效方法，会让未来任务沿旧路走偏。定期在真正使用时局部核查，而不是为手册再建设一套沉重审查系统。

对临时失败尤其谨慎。一次安装受限，说明当前环境缺条件；不能直接升级为“永远不要使用这个工具”。一次小程序成功，也不能升级为“永远用这套框架”。把场景和证据一起保留，经验才不会变成过时命令的收藏夹。

## 动手练习：留下三条，删除两条

从自己真实完成的案例提炼三条方法，每条写明适用条件与观察依据。再删除或改写以下两条：“任何任务都先派三个 Agent”“只要全部测试通过，就可以写功能完成”。最后把短手册用于一次新的小任务，记录一项帮助和一项需要调整的地方。
