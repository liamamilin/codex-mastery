# 第 8 章：提供信息，不等于堆满信息

你有一个文件夹、一份长说明、几十条旧聊天。为了让 Codex“完全理解”，你把它们全部交过去。它读了很多，却依据一段旧想法给任务工具加了云同步。信息并不少，真正缺的是：哪些材料约束当前任务，哪些只是过去的背景？

本章沿用第 7 章的 `my-tasktrail`。你将把调查结果收敛为一条具体任务，增加列表状态筛选，并检查原有行为仍然成立。终点不是整理一份漂亮的资料包，而是让提供的每项信息都服务于这次可验证的改动。

## 先把这次任务与项目愿景分开

当前起点已有添加、完成、列表与 JSON 保存。现在需要的是：`list --status open` 只看未完成，`done` 只看已完成，`all` 看全部；省略参数时保持原来的全部列表。这个描述同时给了新能力与兼容要求。它没有要求标签、账号或界面，也不要求把数据重新组织一遍。

这里的“上下文”可以理解为 Codex 当前能够用来判断的信息，包括你的话、读到的文件和工具反馈。它能看到，不代表应该把每一条都当作当前需求。案例的 `notes/ideas.md` 保留了旧讨论，并明确说那些想法没有实现。这个文件有助于解释过去，但不能代替你刚刚给出的任务。

先在自己的笔记中写一句话：“这次只改变列表显示的选择，数据格式与添加、完成保持兼容。”如果无法写清这句话，先澄清目标；如果已经明确，就不必再要求 Codex遍历所有资料来证明它认真。

## 给它一个有方向的入口

关闭上一章的只读会话，在操作系统终端确认当前目录为 **`my-tasktrail`**，再启动能实施的会话：

```sh
codex --sandbox workspace-write
```

Windows 使用与第 2 章一致的 `codex` 或 `codex.cmd`。App 与 IDE 用户打开同一个工作副本，确认允许当前任务的文件修改。不要在只读会话中反复要求“直接写”，也不要为一个本地改动扩大到与任务无关的权限。

把下面的任务发给 **Codex 输入框**。其中的调查结论请按自己的实际简报替换，不复制未经确认的推测：

```text
请在当前 TaskTrail 副本增加列表状态筛选。
目标：list --status open|done|all；默认 all，与现有列表兼容。
材料：先看 tasktrail.py、tasks.py 和 tests/test_cli.py；
README 用于确认启动方式，notes/ideas.md 的旧设想不是本次需求。
保留 --data 规则、JSON 格式、添加与完成行为，不改 sample.json。
请先指出预计改动位置，再实施并补上必要断言。
运行现有测试，并用一份同时包含两种状态的数据检查筛选。
筛选不应写入数据文件；错误状态值应给清楚反馈且返回非零。
不安装依赖。测试可以使用系统临时目录，交付说明实际命令与结果。
```

这不是一种必须背诵的提示词模板。给出文件入口，是因为上一章已查到它们与问题有关；说明旧设想不是需求，是因为本项目确实保留了容易混淆的背景。换一个项目，就应该换成那个项目真正需要的材料。只说“全面理解以后再做”，反而没有帮助它判断阅读何时足够。

## 怎样判断信息是否值得加入

可以用一个具体问题筛选材料：“它会改变这次实现或验收吗？”参数解析代码会影响新增选项放在哪里；数据结构会决定怎样区分完成状态；现有测试会影响兼容检查；一年前对网页配色的讨论通常不会。排除它，是为当前判断减少噪声，不是宣布它永远无用。

同样要保留限制与失败信息。例如上一章发现数据格式损坏时程序拒绝写入，这个边界值得告诉 Codex，因为筛选不应顺手变成“读取失败就重建空文件”。相反，反复粘贴同一份成功输出并不会增加新证据。可以用一句结论加命令位置，让它必要时直接复查原文件。

如果某个关键问题仍未确认，就直接写未知。“尚未确认空列表输出怎样处理”比“应该和其它工具一样”更有价值。前者引出一次针对性读取或运行，后者把习惯当成了事实。上下文选择不是只给好消息，而是把会改变决定的事实与未知都留下。

## 让验收能区分正确与看起来正确

完成修改后，在 **`my-tasktrail` 的操作系统终端**运行：

```sh
# macOS / Linux；Windows 把 python3 换成 py -3
python3 -B tasktrail.py --data sample.json list --status open
python3 -B tasktrail.py --data sample.json list --status done
python3 -B tasktrail.py --data sample.json list --status all
python3 -B tasktrail.py --data sample.json list
python3 -B -m unittest discover -s tests -v
```

使用未经写入修改的起点样本时，第一条应只有编号 1，第二条只有编号 2；第三、四条应都显示两条。这些是**预期结果**，你的实现是否达到它们，要看真实输出。只用全是未完成的数据检查，会漏掉“无论传什么都显示全部”的假筛选。

再运行一个错误参数：

```sh
python3 -B tasktrail.py --data sample.json list --status unknown
```

它应拒绝该值。macOS / Linux 紧接着运行 `echo $?`，PowerShell 运行 `$LASTEXITCODE`，可查看上一程序的退出码；非零表示这次调用未正常完成。不要在查看退出码以前先运行另一个命令，否则看的可能是别的程序结果。参考成品使用退出码 2，你自己的实现至少应提供明确、稳定的失败结果。

还有一个界面上看不见的要求：筛选不应修改 JSON。请让 Codex在自动测试中对比筛选前后的文件内容，同时保留添加与完成的原检查。列表正确而文件中的已完成任务被删除，仍然是严重错误；它把“暂时不显示”误做成了“从数据中移除”。

## 当它读得太少或太多

若 Codex只改帮助文字，没有找到列表数据来源，补充相关函数或要求它沿实际调用路径读取。若它不停读旧笔记、准备设计账户系统，指出当前任务与验收，要求它回到参数解析、过滤和输出。两种纠偏都要指向缺少或多余的信息，不必升级成几十条永久规则。

遇到 `unrecognized arguments`，先检查你运行的是修改后的副本，且 `--status` 放在 `list` 后；也检查是否误运行了教材 `starter`。起点不认识这个新参数是正常现象，不能把参考成品的预期倒过来套给未修改代码。

若测试通过但手工筛选不对，保留两份证据再比较覆盖范围。测试可能只检查旧功能，也可能用了不区分状态的数据。让 Codex补上能够失败的断言，比把“测试通过”当作停止讨论的理由更有帮助。
