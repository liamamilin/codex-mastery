# 第 13 章：如何读懂进度并在途中介入

屏幕上不断出现文件名与命令，Codex说正在推进，你却越来越不确定：现在打断会不会破坏有效工作，继续等待又会不会只是重复失败？判断进度的关键，不是动作多不多，而是动作有没有减少未知、改变相关对象，或增加完成条件的证据。

本章将执行记录、文件差异和使用行为放到一起。你会在三个情境中作出“继续、调整、停止”的决定，并对自己的任务发出一次具体介入。你不必懂所有代码，但需要能指出下一项行动为什么值得做，以及什么现象说明当前路线已失去依据。

## 从动作看到它提供的证据

“准备检查保存”是意图；读取文件是一次行动；修改差异说明磁盘内容改变；浏览器刷新后仍在，才支持保存路径在该条件下成立。第 1 章的区分在这里再次派上用场。进度不能只按承诺积累，也不能把每条命令都当成一份同等价值的证据。

下面是**为教学构造的示意记录，不是本项目真实 Codex 日志**：

```text
示意｜目标：保存成功后清空表单，失败时保留输入。
示意｜已读取：表单提交入口、写入函数、错误反馈分支。
示意｜已修改：清空操作的位置。
示意｜语法检查通过；尚未实际检查浏览器中的保存失败。
示意｜下一步：用失败分支确认输入不会提前丢失。
```

这里适合继续。它找到相关路径，修改针对目标，并知道还缺什么证据。浏览器尚未检查不等于工作无效；只要下一步能补上缺口，就没有必要为了催促而切换方案。你可以让它继续完成已确定的检查，自己再承担它无法执行的手工部分。

## 看差异，不只看修改了多少行

diff 是文件修改前后的差异，通常用 `-` 表示删除、`+` 表示增加。先通过当前界面的变更列表查看即可；Git 的具体操作留到下一章。对自己生成的项目，先定位与目标有关的函数，再要求 Codex解释变化如何影响使用行为。

下面是**简化示意差异，不是可直接应用的补丁**：

```diff
- 保存成功以后，清空表单
+ 先清空表单
+ 再尝试保存
```

改动很小，却可能让存储失败时的输入丢失。仅有“语法检查通过”解释不了这个行为。你可以问：“这次把清空提前以后，保存失败分支怎样保留输入？请引用实际实现，再做失败检查。”不需要先理解全部页面结构，也能围绕目标审阅一个关键顺序。

反过来，改动较多不一定错误。有时补齐错误反馈需要同时改输入、状态与样式。先看这些变化是否形成同一条使用路径，是否越过本轮范围，再决定要不要收缩。行数是定位线索，不是质量分数。

## 什么时候调整当前动作

第二段仍是**教学示意**。假设故障是“删除后当前列表消失，刷新又回来”：

```text
示意｜再次增加界面重绘。
示意｜语法检查通过。
示意｜实际复现步骤仍然得到：删除后刷新恢复。
示意｜准备把重绘延迟再增加一些。
```

这里值得调整。新的修改还没有解释刷新重新读取的数据，已有观察也没有支持时序假设。介入时别只说“你又错了”，把证据和下一项检查连起来：

```text
先暂停继续增加重绘或延时。
目前事实是：删除后的界面变化正确，但刷新后旧记录恢复。
请沿删除、状态保存、页面读取追踪实际数据，
先给出一个能区分原因的检查，再决定最小修改。
保留已有效的新增行为，不顺便重做整个页面。
```

这段话调整的是调查方向，不是禁止它行动。你提供了能反驳当前解释的观察，也给了下一项有价值的任务。连续失败时，真正该改变的常常是问题与假设，而不是在原指令后加更多强调语。

## 什么时候停止当前尝试

停止适用于继续当前动作会扩大无关变化、破坏已有成果，或关键前提尚未获准的情况。例如只想离线搜索，执行却准备替换整套存储并删除旧数据；又如读错目录后仍准备写入。此时应先停止这项动作，核对位置、范围与已有更改，再选择恢复路线。

停止当前尝试不等于放弃项目。先保留能解释现状的材料：目标、实际改动、最后一次复现、尚未确认的假设。不要顺手清空目录来获得“干净状态”；那里可能还有你或另一项任务的有效修改。下一章会用独立练习介绍版本与回退，这里先做到看清后再处理。

如果某动作只是缺少环境能力，例如没有浏览器，停止反复调用同一不可用入口即可。它仍可以检查代码和数据逻辑，再明确交给你手工操作。工具受限与功能失败是两件事，不能为了把进度写成全绿而伪造浏览器结果。

## 从文件存在，继续看到本次调用是否成功

CSV 案例提供另一种容易误读的进度：旧 `summary.md` 仍在，但新输入含坏数值，本次命令失败。保留旧报告是保护行为，不是新输入分析成功。你应看本次退出码、错误与输入，再决定修数据还是改规则，不能让 Codex仅凭“输出文件存在”就交付。

在自己的 `my-csv-insight` 中，可运行已有检查观察这一区别：

```sh
# 操作系统终端；Windows 将 python3 换成 py -3
python3 -B -m unittest discover -s tests -v
```

测试内部用临时输入制造坏数值，确认旧报告不变；整体测试应通过，不会故意让你的完整检查失败。它提供特定行为的证据，不能替代你对业务口径的判断。制作时四项测试确实通过，读者副本结果仍以实际命令为准。

## 用三个问题作出决定

先问“这一步使哪个未知减少了”，再问“改变是否仍服务于完成条件”，最后问“下一步有什么区分力”。有清楚答案且风险在已授权范围内，通常继续；结果反驳原假设或动作没有信息增量，就调整；对象、范围或前提明显不对，就停止当前动作并恢复可判断状态。

不需要规定每隔几分钟强行打断，也不需要把失败次数当魔法数字。一次有力反例就可能足以换方向，多次小失败也可能都在排除不同原因。你判断的是证据积累，而不是聊天长度或重试计数。

## 动手练习：留下一个可解释的介入决定

选自己正在推进的 A、B 或 C 副本，找一段真实执行记录和一处实际变化。写三句话：这段记录支持什么；还不能说明什么；现在选择继续、调整还是停止，并给下一项具体动作。没有真实运行记录时，可以评价本章的示意情境，但必须写明这是情境判断，不能记作实际任务已验收。
