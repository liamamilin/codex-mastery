# 第 14 章：变化范围、版本和回退

Codex 能一次修改多个文件。便利也带来一个实际问题：你怎样知道它改了哪些地方，发现方向不对时又怎样回来？如果答案只是“让它再改一次”，你还没有留下可靠的恢复位置。

Git 把某个时刻的文件状态记成提交。你可以先观察当前变化，再决定哪些进入一个提交，之后恢复指定文件或用新提交撤销旧提交。本章只学这些最少操作，完成一个可回退的练习修改。提交不会自动上传，也不会证明程序可用；它的价值是让变化可以比较、解释与恢复。

## 先进入不会碰到原项目的练习仓库

需要 Python 3、Git 2.28 或更新版本，以及完整教材。先在操作系统终端运行 `git --version`，确认 Git 可执行。不要在自己的工作项目直接练习恢复命令。

在**教材仓库根目录**运行：

```sh
python3 -B extensions/git-lab.py
```

Windows 已安装 Python Launcher 时用 `py -3 -B extensions/git-lab.py`。辅助脚本将案例 B 起点复制到系统临时目录，创建新的 Git 仓库与基线提交，只在新仓库设置练习身份，不修改教材或全局 Git 配置。它不连接远端，也不删除旧练习。

终端最后一行是新目录的绝对路径。复制它，执行 `cd "刚才输出的完整路径"`；PowerShell 可用 `Set-Location "刚才输出的完整路径"`。下面所有 Git 命令都在这个新目录运行：

```sh
git status --short
git log --oneline -1
```

初始状态应没有待处理文件，历史中应有基线提交。没有输出的 `status --short` 表示工作区与索引相对当前提交没有这些变化，不是命令失效。若脚本报错，先看找不到 Git、源目录还是提交失败，保留新目录；不要转而在教材根目录“试一下恢复”。

## 变化、暂存与提交，是三个不同位置

用编辑器在练习 `README.md` 末尾添加一句“练习：本轮先核对变化范围。”，再在 `notes/ideas.md` 末尾添加“保留：这是另一项练习记录。”。现在运行：

```sh
git status --short
git diff -- README.md
```

状态会列出两个修改文件；diff 只展示指定 README 相对暂存区的变化。新增行前面是 `+`，删除行前面是 `-`。这不是要求你逐字符审代码，而是先回答：实际变化是否落在本轮目标范围？为什么另一个文件也发生变化？

工作区是眼下的文件，暂存区是准备进入下一次提交的选定内容，提交则是已经记录的版本。

![工作区、暂存区与提交之间的关系：取消暂存保留文件修改，恢复覆盖指定内容，撤销提交形成新历史](./public/diagrams/version-trail.svg)

用明确路径暂存本次说明：

```sh
git add -- README.md
git diff --cached -- README.md
git status --short
```

`--cached` 检查待提交内容。此时另一个笔记仍未随它暂存。状态短格式有两列，第一列对应索引，第二列对应工作区；同一个文件还可能在暂存后继续被修改。因此看到文件名就提交还不够，要核对真正进入提交的那份差异。

暂存也不是一份独立备份。如果暂存后又编辑文件，两份内容会不同，下一次提交记录的是索引中的内容。让 Codex 在提交前同时核对两份差异，尤其留意它是否把临时输出、个人配置或与本轮无关的资料也选进去了。对你不了解的文件，先调查用途再决定，而不是用“全部加入”省去这个判断。

不想现在提交，可以取消暂存：

```sh
git restore --staged -- README.md
```

重新打开 README，刚才那句话仍在。取消暂存改变的是选定内容，不等于丢弃文件修改。这是最容易混淆、也最值得亲眼确认的一处区别。

## 恢复一个文件前，先保存你还需要的内容

本轮决定放弃 README 的练习句，但保留笔记。先在编辑器把当前 README 另存到**这个临时仓库之外**，例如它的父目录，确认备份可打开。然后核对当前目录和 diff，只在刚创建的练习仓库执行：

```sh
git restore --source=HEAD --worktree -- README.md
git status --short
```

这会用当前提交中的 README 覆盖工作区对应文件。它会丢弃该文件尚未保存到提交的变化，所以先备份并确认范围。执行后 README 的练习句消失，`notes/ideas.md` 中的保留句仍在。这里使用明确路径，没有清理其他文件，也没有让整棵工作区回到旧状态。具体语义见 [Git restore 文档](https://git-scm.com/docs/git-restore)。

如果恢复结果与你以为的基线不符，先查看 `git log` 与备份，确定 `HEAD` 指向的是什么。不要把“恢复”理解成 Git 能猜出你心中的正确状态。未跟踪文件也不会因为普通 diff 没显示就自动安全；`git status` 中的 `??` 仍需单独判断。

## 已提交的变化，用新的历史撤销

先将笔记作为一项独立练习成果记录下来：

```sh
git add -- notes/ideas.md
git commit -m "lab: keep independent exercise note"
```

再次编辑 README，添加“练习：这次提交只记录说明变更。”，然后：

```sh
git add -- README.md
git diff --cached -- README.md
git commit -m "docs: record review exercise"
git status --short
```

确认此时工作区干净、最新提交就是刚才的 README 变更，再执行：

```sh
git revert --no-edit HEAD
git log --oneline -4
```

你会看见一个新的撤销提交；被撤销的原提交仍在历史里，README 回到此前内容，已经独立记录的笔记仍保留。`revert` 用反向变化形成新提交，适合保留变更过程。它与覆盖工作区某个文件的 `restore` 解决不同问题；不要只因两者都叫“回退”就互换。见 [Git revert 文档](https://git-scm.com/docs/git-revert)。

本练习顺序已在 macOS、Git 2.54.0 的独立临时仓库实际执行：取消暂存后内容保留，指定文件恢复没有动笔记，提交后撤销产生新历史。Windows 命令路径已提供，未在 Windows 本机复测。你的提交哈希和临时目录会不同，以文件内容与历史关系判断结果。

## 让 Codex 保护任务开始前的工作

真实项目一开始可能就有你的未提交修改。先让 Codex 读 `status` 与 diff，记录这份起始状态，再实施本轮任务。可以发给它：

```text
先检查当前 Git 状态，区分任务开始前已有的改动与本轮新增改动。
本次只处理指定需求，不将无关文件打包进提交。
如果需要恢复，先说明具体路径、来源版本与会被覆盖的内容，
保留我尚未提交的工作；不要直接清理整个工作区。
```

一个文件里也可能混合两个人或两次任务的修改。此时按文件恢复仍可能过宽，应先备份并分离差异，或人工保留需要的段落。让 Codex 说“我会小心”没有提供保护；明确路径、已知基线和实际备份才有恢复依据。

## 动手：交付一个可以回来的位置

重新生成一份临时练习。自己完成两处修改、只暂存一处、取消暂存、备份后恢复指定文件，再提交另一处。要求 Codex 解释每一步改变了工作区、暂存区还是历史，你用文件与 diff 核对。

完成时留下目录、提交说明、尚未提交内容及恢复选择。能够说出“我准备撤销哪一份变化，哪些现有工作必须留下”，就比只会记一条回退命令更接近掌控。
