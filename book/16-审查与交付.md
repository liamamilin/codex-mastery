# 第 16 章：代码审查、解释和交付

“我看不懂每一行 Python，还能审查 Codex 的修改吗？”可以，但需要把问题问到合适的位置。你可以判断结果是否满足需求、变化是否越界、错误时会发生什么，以及后来的人能不能运行。遇到实现细节，再要求 Codex 引用代码解释，而不是让“代码看起来很专业”代替判断。

本章从案例 B 的状态筛选交付开始。你会把需求、diff 和实际检查对齐，了解 Codex review 的作用，最后写出一份别人能复查的交付说明。前提是你有案例 B 的工作副本或参考修复版、Python 3，以及第 14 章的 Git 基础。

## 先审查它承诺改变的行为

案例 B 的目标很窄：`list --status open` 只显示未完成，`done` 只显示已完成，`all` 与省略参数保持全部。筛选应当只改变展示，不重写任务文件、不改变编号，也不影响添加和完成操作。

先把这一段需求放到审查窗口旁边。不要从“代码有没有用某种高级写法”开始。一个很漂亮的重构如果顺便改了数据格式、删除了未匹配任务，仍然没有完成这个任务。

如果直接按第 7 章复制了 `my-tasktrail`，先不要假定它有独立 Git 历史；位于教材仓库内也不等于拥有自己的修改基线。可以在第 14 章生成的独立临时仓库中完成同样的筛选改动后审查，或用编辑器比较自己保留的改前与改后文件。只有确认了目标仓库与基线，才使用下面的 Git 差异。

在你的**Git 工作副本目录**执行：

```sh
git status --short
git diff --stat
git diff
git diff --cached
```

分别核对文件范围、具体变更及已暂存内容；未跟踪文件仍需从 `status` 找到后阅读。若看到样本数据被改，追问是必要格式迁移、测试误写，还是运行时无意产生的变化。不要仅因文件“不属于代码”就把它忽略。

如果你只有教材下载文件，可以用编辑器比较 `cases/B-tasktrail/starter/` 与 `solution/`，但这只能审查参考方案，不代表自己的工作副本已经采用并验证了相同修改。

## 要求解释一个具体因果关系

可以发给 Codex：

```text
请审查这次 TaskTrail 状态筛选改动，先不修改。
对照需求与实际 diff，重点检查：默认行为是否保留，
筛选是否只影响显示，错误状态是否拒绝，数据文件是否被意外写入。
每个问题给出触发条件、实际文件或函数、影响与最小验证方式。
没有证据的问题请作为待确认，不将风格偏好写成缺陷。
```

实际参考实现把筛选放在 `tasktrail.py` 的列表分支，先 `read_tasks()`，再在内存中按 `done` 过滤，最后打印；没有沿这条分支调用 `write_tasks()`。这能解释为什么筛选不应删数据。你仍要通过运行与数据对照验证，而不是只听它口头保证“不会影响存储”。

当它说“可能有问题”，要求落到可触发条件。例如“空匹配时会输出误导信息”可以用全部任务已完成后筛选 open 检查；“代码不够优雅”则未必值得打断交付。审查应优先找影响结果的问题，避免把所有建议变成阻塞项。

## 当期 Codex review 入口

截至 **2026-10-25**，本机 Codex CLI `0.154.0` 实际执行 `codex review --help`，确认有以下入口：

```sh
codex review --help
```

帮助中包含 `--uncommitted`、`--base <BRANCH>`、`--commit <SHA>`，用于选择未提交变化、相对基准分支或某个提交。它们的当期说明见 [OpenAI 官方 CLI reference](https://learn.chatgpt.com/docs/cli/reference)。本章只执行帮助核对，没有另行运行模型审查或声称得到审查结论。

如果你的账号与环境已可用，并愿意消耗相应使用额度，可以在**目标 Git 仓库目录**选择一种范围：

```sh
codex review --uncommitted
```

这不是静态本地命令；它会调用配置的 Codex 审查能力，使用方式与可用性以当前客户端、账号和组织配置为准。不要照抄一个不存在的分支名，也不要同时堆多个目标参数。当期官方参考还将自定义 `PROMPT` 与这些目标列为互斥，不要在带目标的命令后直接追加一段审查要求。先看自己版本的帮助，核对审查实际针对的范围；App 或 IDE 中用当前界面提供的审查入口，并记录所选差异。

专门的审查能换一个视角发现遗漏，但它仍是模型判断。没有发现问题不等于证明没有问题，发现的问题也要核对触发条件。你可以请它找“筛选时误写数据”的风险，然后用运行结果确认，而不是要求它给一张“无风险证明”。

## 把发现转成可验证的处理

在**案例 B 的 solution 目录**，可先运行参考检查：

```sh
python3 -B tasktrail.py --data sample.json list --status open
python3 -B tasktrail.py --data sample.json list --status done
python3 -B tasktrail.py --data sample.json list --status all
python3 -B -m unittest discover -s tests -v
```

Windows 将 `python3` 换成 `py -3`。核对 open 与 done 分别显示不同编号，all 显示全部。若审查指出读取后写回可能破坏数据，可在工作副本中备份数据，对比筛选前后的字节或哈希；不能只因列表看起来正确就略过存储副作用。

审查发现真实缺陷后，让 Codex 针对它修复，再运行触发该问题的最小检查与受影响的邻近行为。新的 diff 仍需要看：一次修复可能加进不必要的迁移或改动其他命令。不要一收到审查结果就无条件接受所有修改建议，也不要因为实现者和审查者意见不同，就让它们无休止互相说服。

## 一份交付说明应该让别人接得住

交付的第一句解释具体变化和用户结果，例如：“列表现在可按 open、done、all 筛选；省略参数仍显示全部，筛选不修改 JSON。”随后给出启动位置、实际执行命令与关键结果，再写未覆盖范围和已知限制。

下面是**交付写法示意**，其中结果需要换成自己的真实观察：

```text
结果：在当前 TaskTrail 副本增加列表状态筛选，默认行为保留。
改动：命令参数与列表显示分支；数据格式未作迁移。
验证：在本副本目录运行……；open 显示……，done 显示……；
数据文件对照……；自动测试……项通过。
限制：未在 Windows 本机运行；不支持并发写同一文件。
继续：从……目录、……提交开始；下一项需求尚未实施。
```

这不是要求每次都填写一张复杂表。小修改用一段话即可，只要别人能分辨“已写”“实际跑过”和“还没验”。如果有失败，不要把它藏在几十行成功日志末尾；先说明它影响哪个完成条件，当前还能使用什么。

## 动手：做一次有结果的审查

选择自己已经完成的一次案例 B 修改。先不改代码，让 Codex按需求、差异与失败模式审查。选出一条最有实际影响的发现，亲自复现；若没有有效缺陷，就记录审查范围与已执行检查，不需要为了凑成果制造问题。

最后写一段交付说明，让另一位读者只按说明启动并检查一次筛选。若他还需要追问“在哪个目录”“用哪份数据”“这个结果真跑过吗”，就补那一处。有效审查把风险落到行为，清楚交付则把成果变成别人可以继续使用和维护的工作。
