# 第 6 章：给 Codex 的任务说明怎么写

“我已经写了一大段，为什么它还是做偏了？”任务说明长，不代表重要信息齐全。你可能规定了颜色、技术名词和检查轮数，却没有说明在哪个目录工作、当前哪里有问题、做完怎样判断。

另一种情况是只有一句“把工具弄好”，然后希望 Codex 理解没有说出的偏好。本章用同一个 LinkShelf 搜索任务比较三种写法。完成后，你应能改写一段含糊指令，也能删掉一段过度限制中的无效要求，保留足够的目标、上下文和证据。

## 第一种：让模型替你猜重要选择

下面的任务过于含糊：

```text
帮我把链接工具弄好，搜索要更高级，做得专业一些。
```

“链接工具”没有定位文件，“弄好”没有指出缺口，“高级”没有说明使用场景。模型可能正确猜中，也可能添加语义搜索、引入在线服务，或只美化输入框。即使你最后觉得不满意，也难以指出它没有满足哪一条约定。

改进并不需要一开始就写完整规格。先补足你真实知道的部分：“工作副本是 my-linkshelf；我想用记得的一段标题或网址找回收藏；还没有确认当前是否支持。”未知可以明确保留，让调查成为第一步。假装知道现状，反而容易让它去修一个不存在的问题。

这里应当把[第 4 章](./04-模糊意图.md)与实施分开。如果连想解决哪种麻烦都未确定，就先让它比较方向。已经确定要标题与网址搜索，才进入本章的实施说明。

## 第二种：把可选择的办法全部锁住

另一种写法看起来很严谨：

```text
你是顶级工程师。无论项目现状如何，先写20页架构文档，
建立七份检查表，执行五轮审查，每改一行都停下来让我批准。
必须按我指定的十个函数名称重写所有文件，再实现搜索。
不允许提出替代路线，必须一次成功。
```

它增加了活动，却没有增加可检查的结果。对于一个已有原生页面的小改动，先重写全部文件会扩大回归范围；规定审查轮数也没有告诉审查应寻找什么。逐行批准会让人把注意力耗在局部，却仍然可能漏掉“刷新后条目丢失”。

有价值的过程约束应当对应具体原因。例如，“沿用现有原生页面，不新增运行时后端”，直接服务于本机静态工具的条件；“保留原有收藏，不清空整个 localStorage”，直接保护已有数据。“必须一次成功”则无法在不确定任务里提供行动方法。更有用的要求是失败后保留复现步骤与错误，改变没有证据支持的假设。

你不必把方案选择全部交出去，也不必逐条控制。把真正影响任务结果的条件留下，其余让 Codex 根据文件和反馈组织。

## 第三种：给出完成状态与行动空间

这是同一任务的一种恰当写法。以下为**可复制的教学任务说明**，不是已经执行过的模型对话：

```text
我的工作副本在 my-linkshelf。新增、刷新保存和删除已按第3章检查；
我想凭标题片段或网址找回记录，尚未确认本版本有无搜索。
请先查看现有文件与行为，再补齐不足，不复制参考成品覆盖我的目录。
输入关键词只显示匹配标题或网址的记录，清空恢复全部，无匹配有提示；
保存成功后清空搜索，让新条目可见；筛选不应修改保存的数据。
沿用原生 HTML/CSS/JavaScript 与本地存储，不增加账号或在线服务。
技术组织按现有项目选择；发现影响范围的重要取舍时说明依据。
完成后实际检查搜索与保存的衔接，再检查新增→刷新→删除→刷新。
请区分实际执行的检查与需要我在浏览器完成的部分。
```

发送之前先修改第一句。只有你确实完成第 3 章验收，才能写“已检查”；尚未检查，就改成“据当前代码实现了这些行为，请先验证”。引用不真实的前提，即使句式很好，也会让后面的工作建立在错误基础上。

如果已经在 `my-linkshelf` 中打开 Codex，路径可写成“当前目录”；如果会话位于教材根目录，应保留完整相对路径。路径不是装饰信息，它决定实际修改对象。需要启动程序时，继续采用[第 3 章](./03-第一次成果.md)的同一服务命令与浏览器来源。

## 这份说明为什么够用

开头的现状告诉 Codex 有什么可保留，未知告诉它哪里需要先调查。中间的使用行为提供终点，范围约束避免引入本轮没有必要的服务。末尾的验证要求让“完成”落到实际检查，而不是一段漂亮总结。

它没有规定每个函数、工具调用顺序或固定审查次数，因为你真正关心的是搜索怎样与收藏行为衔接。若现有代码已经满足要求，正确结果可能是一份检查记录和零项修改；不能为了显得做了事而强制重写。

这也不是每次都需要填写的模板。一个标题错字，只需说清位置和改法。一个未知的刷新故障，需要更多复现条件与观察。任务复杂度决定说明深度，固定字数不会自动提升效果。

下方练习可比较三种写法，并尝试改写。组件里的反馈是教学规则在本地给出的判断，不会把你的文字发送给 Codex，也不能代替一次真实任务的结果。

## 让问题发生在真正需要选择的地方

好的任务说明会减少无意义的来回，但不会消除所有询问。如果你没有指定按钮的圆角，Codex 可以沿现有风格继续。如果两种方案分别意味着“只在电脑本地保存”和“上传到外部账号”，它们改变数据去向与使用前提，就需要把取舍摆出来。

还有一些未知可以通过检查解决，例如项目入口、现有存储键、是否已有搜索。此时让它先读文件，比问你“请告诉我全部架构”更有效。只有你知道的个人偏好、未提供的材料或必要授权，才值得向你索取。

你可以明确说：“材料里能查明的问题请先调查；需要改变本轮范围、增加费用或公开发布时，先给具体方案与影响。”这表达协作偏好，不会自动绕过宿主权限、组织策略或外部服务授权。出现权限拒绝时，应看被拒绝的真实动作，再决定替代路线或必要授权。

## 在工作途中，用新事实更新说明

任务说明不是一次写完就不能动的合同。假设 Codex 调查发现已有搜索，但保存新条目时仍被旧筛选隐藏。此时不必重发整段任务，补充：“搜索已存在，本轮只处理保存后的显示衔接，保留匹配规则。”

如果结果与你预期不同，优先反馈操作与现象。“颜色不是我要的”和“新增看不见”是不同问题；“新增后输入框清空，但列表没有出现，清空搜索后才看到”能显著缩小调查范围。直接要求“再专业一点”会把已获得的证据重新模糊掉。

修改范围也要随事实收敛。若只有一处衔接缺失，不必让它再完成一遍所有功能；若发现存储无法读取，应先处理读取问题，避免在未知数据状态上继续叠加搜索。

## 动手练习一：给含糊任务补关键信息

把“导出不好用，帮我搞定”改成一段最多六句话的说明。使用参考成品已存在的 JSON 导出，自己选择一个具体困扰：找不到文件，或下载内容与当前收藏不符。明确哪项是你真的观察到的，哪项还需要检查。

示例可写：“我在参考成品中点击‘导出 JSON’，没有在浏览器下载列表找到文件。请先检查下载是否被阻止与导出事件是否触发，不要先增加导入功能。保留现有收藏，检查两条测试记录导出后能否被 JSON 读取，标题和网址是否一致。没有浏览器工具时给我手工检查步骤，报告未验证部分。”其中“没有找到文件”必须换成你的真实观察；不能仅为套句式捏造故障。

## 动手练习二：从过度限制中留下必要约束

改写下面的教学情境：“删除后刷新会回来；请重写所有文件、加延时重绘、连续审查五次，每改一行都问我。”这个故障是构造的问题报告，不是在宣称当前参考成品存在该缺陷。

<summary>展开参考反馈</summary>

可以改为：“删除后当前页面消失，刷新却恢复。请先复现，查明删除后的写入与刷新读取路径，用证据区分原因，再做最小修复。保留其他收藏与新增行为；检查删除→刷新不恢复，并确认另一条记录仍在。不要先假定延时能解决。”它保留数据边界与验证要求，删掉没有依据的重写和次数要求，也没有把猜测预设为修复方法。

</details>

完成这两次改写，你应当更容易看出一份任务说明缺什么、多什么。接下来面对陌生项目时，就可以先让 Codex 用实际文件补全现状，再决定如何推进。当前已开放的阅读入口见[课程目录](./curriculum.md)。
