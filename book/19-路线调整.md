# 第 19 章：换路线、降范围与及时止损

你已经检查了几轮，任务却还没完成。此时最难的决定，往往不是下一行代码怎么写，而是是否继续当前路线。前面花了很多时间，会让人想再试一次；看到失败，又容易想把所有代码推倒重来。两种反应都可能绕开了真正的问题：下一步能带来什么新信息？

本章承接[第 18 章的假设检查](./18-停止无效修补.md)。我们以 Phantom Delete 已定位的保存故障为起点，比较继续修复、换验证路线、缩小范围与停止当前尝试。完成后，你应能写出一段有事实依据的路线调整说明，并让已有成果留下来，而不是只报告“还在努力”。

## 已经知道根因时，继续可能最便宜

案例 D 的 `starter/core.mjs` 中，`deleteRecord` 过滤出新数组并返回，缺少将结果保存的调用。`solution/core.mjs` 则在返回之前调用 `saveRecords(storage, key, next)`。两个版本的最小差异只有这一条写入。这是当前案例文件的事实，不意味着所有刷新故障都能用一行修复。

如果你已经按上一章证明“内存删除后为两条，存储仍为三条”，并定位到这条路径，就有充分理由继续做针对性修复。目标没有变化，问题范围已经缩小，验证动作也明确。换框架、增加数据库或重画页面，都不会提供比补齐保存路径更直接的证据。

在自己的 `my-phantom-delete/starter/core.mjs` 中继续，而不是改教材原始故障版。发给 **Codex 输入框**的指令可以是：

```text
已确认删除后的数组没有写回本案例专用存储。
请只在当前工作副本补齐删除的持久化路径，保留现有校验与错误处理。
检查删除→重新读取不恢复，其他两条仍在；
再检查新增后重新读取、删除到空列表后重新读取。
暂不改页面样式。实际浏览器刷新若不能执行，单独报告待验。
```

这里继续的是一个已经有证据的方向，不是继续同一种无依据补丁。修改前后若出现新的存储异常，就重新检查保存调用是否真正成功，不能因为差异只有一行就跳过验证。

## 换路线时，保留原来的目标

下面是一个**教学情境**：工作环境没有可用的自动化浏览器工具，Codex 能运行 Node 测试，却无法亲自点击页面。它连续尝试安装浏览器依赖，每次都被组织网络策略阻止。这不是本次真实 Codex 多轮日志，也不是案例必须联网才能运行的声明。

此时继续改删除代码，并不能解决验证工具缺失。更合理的替代路线，是由程序测试检查数据读写，再由你用已有浏览器完成同样的删除与刷新验收。改变的是谁来执行检查，以及如何获得证据；“删除后刷新不恢复”的目标没有被降低。

案例 D 的逻辑检查可以在**教材根目录的操作系统终端**执行：

```sh
node --test cases/D-phantom-delete/tests/delete.test.mjs
```

它不下载软件、不需要 API Key，但需要 Node.js 18 或更新版本。测试覆盖教材的故障版与参考修复版，不会自动检查你的工作副本。若要验证副本，让 Codex 先核对测试的导入路径，在副本中调整对应测试目标；不要拿参考答案通过的结果替自己的改动背书。

人工检查沿用案例 README：在教材根目录运行 `python3 -m http.server 4176 --bind 127.0.0.1 --directory my-phantom-delete`，Windows 将 `python3` 换成 `py -3`；浏览器打开 `http://127.0.0.1:4176/starter/`，完成后在服务终端按 Ctrl+C 停止。服务未启动时先检查 Python 和端口，不把环境问题当成保存逻辑失败。

参考测试与手工操作一起，可以逐渐补齐证据。如果手工条件也暂时没有，交付应写“数据逻辑已检查，浏览器验收待完成”。替代路线不能靠改变措辞，把没有发生的观察变成通过。

## 降范围时，明确哪部分承诺改变了

再看另一个**教学情境**：修复删除期间，使用者提出“顺便加上跨设备同步、自动回顾与动画”。新增愿望不等于当前实现突然失去价值。你需要先判断它们是新的阶段，还是说明原目标本就理解错了。

如果使用者仍需要一个本机教学工具，可以先交付保存故障修复，延后同步、回顾与装饰。这是把本轮范围收回已约定的目标。保留删除与刷新的完整验收，不能用“先做一半”交付一个仍会恢复条目的删除功能。

如果使用者真正的问题是手机收藏、电脑读取，那么本地保存无法满足核心使用场景。你应说明现有模型的限制，比较可接受的替代流程，交由使用者决定是否开启另一项任务。不要自行引入外部账号或付费服务，把重要产品变化藏在技术调整中。

范围缩小需要使用者看得懂的表述，例如：“本轮交付本机删除修复，已保留的两条收藏不受影响；同步暂不实现，因此换设备无法看到这些记录。”它比“先上线 MVP”具体，也不需要用一大份审批表代替对话。

## 停止当前尝试，需要留下可恢复的位置

停止不是把目录删除，也不是宣称任务已经完成。它表示在当前约束下，继续同一路径没有可辩护的下一步。例如，必须由授权持有人开放的访问缺失，且没有等价材料；或者核心目标已变化，旧实现无法再回答当前问题。

遇到这类情况，先保存能复用的成果：可复现步骤、实际错误、已确认的根因、最小修改、运行方法、尚未验证的部分。别为了“干净”清空浏览器存储或撤销别人的修改。案例 D 的“恢复初始样本”会覆盖当前版本练习数据，只有要重新开始合成样本实验时才使用，不是通用的止损按钮。

你可以要求 Codex：

```text
先停止当前工具安装路线，不再重复相同请求。
请保留已有实现和测试结果，记录阻碍实际发生在哪个动作，
哪些目标仍未验证，以及具备什么条件后能继续。
给出一个不依赖这项工具的可行下一步；没有时如实说明。
```

重要的是停止哪一条路线，而不是笼统地让全部工作永久结束。浏览器工具不可用时，正文、样本和数据测试仍可能继续；缺少必要授权的依赖动作则应等待相应决定。不要把等待条件写成“以后再看看”。

## 用信息增量判断，不用次数判断

一次失败就可能推翻假设：存储快照根本没变，已经足以质疑“只是重绘慢”。多次尝试也可能有价值：每次分别检验存储键、异常处理和初始化分支，确实在排除原因。次数本身不能区分这两种情况。

给每次继续一个具体理由：下一步检查哪项未知，它的不同结果将怎样改变选择。如果答案仍是“再试一次可能会好”，先暂停，回到事实与假设。已经投入的时间可以解释你为什么着急，却不能证明下一次相同动作更可能有效。

## 动手练习：作出一次可以解释的调整

请选择自己的真实案例，或使用下面的**教学情境**：删除遗漏写入已定位，参考修复的数据测试通过；你的副本尚未运行浏览器；自动化浏览器无法使用；使用者又希望本轮加入动画。写四句话：当前事实、选择的路线、保留与延后的成果、下一项可检查动作及继续条件。
