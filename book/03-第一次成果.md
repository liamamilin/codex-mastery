# 第 3 章：第一次从指令走到可见成果

现在你已经能定位教材目录，也能让 Codex 读取一份任务。接下来做一件完整的小事：输入标题和网址，保存到列表，刷新后仍然找到它，删除后刷新也不会回来。

这个范围足以经历一次真正的协作，又小到可以逐项检查。我们把它叫作 LinkShelf 基础版。暂不引入账号、云同步或数据库，因为它们不会帮助你判断第一次保存是否完成。你最后需要拿到的，是自己的可运行文件和一份实际验收结果。

## 两种起点，先选一条

要训练从目标到实现，使用“自己制作”路径：把 `starter` 复制为独立工作副本，让 Codex 在副本中完成任务。想先了解完成形态，使用“运行参考成品”路径：直接打开 `solution`，完成相同的手工验收。参考成品用于对照，不代表你已经完成了一次 Codex 实施任务。

以下操作以前一章的 CLI、Python 3 和浏览器准备为前提。运行参考成品无需登录 Codex；自己制作需要可用的 Codex 会话。使用两个终端，一个交给 Codex，一个运行网页服务。在每个终端中都先进入教材根目录。

## 自己制作：把起点复制到独立目录

先确认教材根目录中**尚无 `my-linkshelf`**。如果已有同名练习，用另一个新名称，并同步替换后文路径，不要覆盖上次成果。

**macOS / Linux，操作系统终端：**

```sh
cp -R cases/A-linkshelf/starter my-linkshelf
cd my-linkshelf
codex --sandbox workspace-write
```

**Windows PowerShell：**

```powershell
Copy-Item -Recurse cases/A-linkshelf/starter my-linkshelf
Set-Location my-linkshelf
codex --sandbox workspace-write
```

现在 Codex 的工作目录是你自己的副本。`workspace-write` 让它在当前允许的工作区中修改文件；实际权限仍以宿主和组织配置为准。App 或 IDE 用户打开这份副本，完成同样的任务即可。

将下面的文字发给 **Codex 输入框**：

```text
请阅读 TASK.md，在当前目录实现 LinkShelf 基础版。
使用原生 HTML、CSS、JavaScript，浏览器本地存储，
无需安装依赖或连接外部服务。
用户可以输入标题和 http/https 网址，保存后出现在列表；
刷新后仍在；能删除条目，删除后刷新也不恢复。
空标题或不合要求的网址应有明确反馈，不保存错误条目。
先完成这一条使用路径，再考虑外观；本次不做账号或云同步。
请说明修改了哪些文件，给出本地启动方式。
能够执行的检查请实际执行；没有浏览器时明确写出待人工验收，
不要把阅读代码当成新增与刷新已经通过。
```

这里给出了实现边界和四种可观察行为，却没有指定每个函数的写法。技术细节由 Codex 在当前规模内组织。你负责保留完成条件，避免它为了“更完整”扩出不必要功能。

它工作期间，留意是否真的产生了文件；是否开始安装任务没有需要的框架；检查命令证明的是语法，还是浏览器行为。如果它只生成一个解释而没有落盘，直接要求：“请把实现写入当前目录的实际文件，再说明入口。”

## 启动本地网页

在**第二个操作系统终端**进入教材根目录。下面的服务只监听本机回环地址，不需要公开网络。

**自己制作的副本，macOS / Linux：**

```sh
python3 -m http.server 4174 --bind 127.0.0.1 --directory my-linkshelf
```

**自己制作的副本，Windows PowerShell：**

```powershell
py -3 -m http.server 4174 --bind 127.0.0.1 --directory my-linkshelf
```

在浏览器地址栏打开 `http://localhost:4174/`。命令运行后终端持续等待，是服务器正在提供文件；保留这个窗口即可。返回该终端按 **Ctrl+C** 停止服务。目录与绑定地址参数可参阅 [Python 官方 `http.server` 文档](https://docs.python.org/3/library/http.server.html)。

**如果选择运行参考成品**，在教材根目录改用下面的目录参数。先停止已有的 4174 服务，避免端口冲突。

```sh
# macOS / Linux
python3 -m http.server 4174 --bind 127.0.0.1 --directory cases/A-linkshelf
```

```powershell
# Windows PowerShell
py -3 -m http.server 4174 --bind 127.0.0.1 --directory cases/A-linkshelf
```

此时浏览器打开 **`http://localhost:4174/solution/`**。两条路径的目录不同，所以浏览器地址也不同。不要把副本的根地址和参考成品的子目录混用；也不要双击 HTML 后用 `file://` 作为本章的验证路径。

![LinkShelf 参考成品的真实浏览器界面，包含新增表单与链接列表](./public/screenshots/linkshelf-desktop.png)

图示是参考成品的真实界面。你自行生成的排版可以不同，下面按功能验收。参考成品的输入标签为“标题”“网页地址”，新增按钮为“保存到链接架”，每条记录旁有“删除”。

## 用四次操作证明关键路径

先不要导入自己的真实收藏。使用两条容易辨认的样本，每次只检查一种变化。

| 步骤 | 亲手操作 | 看见什么才算通过 |
| --- | --- | --- |
| 新增 | 标题填“示例网站”，网址填 `https://example.com`，点击保存 | 列表出现对应标题与网址 |
| 刷新 | 刷新当前标签页 | 同一条记录仍存在 |
| 再新增 | 标题填“学习资料”，网址填 `https://example.org`，点击保存 | 两条记录都能看到 |
| 删除 | 删除“示例网站”，再刷新 | “示例网站”不再出现，“学习资料”仍在 |
| 错误输入 | 标题填“错误样本”，网址填 `javascript:alert(1)`，尝试保存 | 有反馈，列表不增加该条目 |

删除第一条时若第二条也被误删，说明列表虽然发生了变化，目标行为仍未完成。第二条样本的作用，是让你能区分“正确删除指定对象”和“简单清空列表”。多记录检查能暴露单条样本不易发现的问题。

如果浏览器原生校验直接阻止错误输入，也是一种有效反馈；无需要求反馈文案与截图逐字一致。关键是错误条目没有落入列表，已有的合法条目还在。记录实际看到的结果，某一项失败就写失败，不要用页面漂亮来抵消它。

参考成品额外提供标题或网址搜索，以及“导出 JSON”。可输入“学习”检查匹配，再清空搜索恢复全部条目。导出会下载当前数据快照，本阶段**没有导入功能**。这些是参考成品的可选扩展，不是自行实现基础版的必做要求。

## 刷新为什么值得单独检查

页面此刻显示的列表，通常保存在 JavaScript 的内存状态中；刷新后，这份状态会重新创建。要恢复收藏，应用必须把数据写到持久化位置，并在加载时读回来。本案例用浏览器的 `localStorage`，即按站点来源保存字符串的小型存储。下面的图把“屏幕显示”和“保存路径”分开画了出来。

![输入、内存列表、localStorage 与刷新读取的数据路径](./public/diagrams/storage-path.svg)

因此，“新增后能看见”只检查了当前页面，“刷新后还在”又检查了写入与读取的衔接；“删除后刷新不回来”则检查删除是否也同步保存。后面的故障课会让你专门调查这个衔接。此刻先把观察做准确，不必抢着背 API。

这些数据只在**当前浏览器、当前站点来源**中保存，不是云同步。`localhost:4174` 与 `localhost:4175` 的端口不同，存储就不同；`localhost` 与 `127.0.0.1` 也不是相同主机名。换浏览器、无痕窗口、清除网站数据，都可能看不到原来的收藏。做刷新验收时，保持浏览器与地址不变；需要保留重要数据时使用备份，不把浏览器存储当作永久档案。[MDN 的 localStorage 说明](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)记录了这些来源与存储策略限制。

参考成品使用专用存储键 `codex-mastery:linkshelf:a1:v1`。自己的实现可以选择另一专用键；为了避免两个练习的数据混在一起，不要要求所有版本共用同一个键。

## 失败时，先增加信息

若网页打不开，先回终端看服务是否仍在运行；如果是“地址已被占用”，先确认是否开着上一次服务，可 Ctrl+C 停止后再启动。也可把命令和浏览器地址一起改为 4175，但这会改变存储来源，原数据不会自动跟随。

若看到目录列表，通常是服务目录层级不对或没有 `index.html`；若参考成品 404，核对是否使用 `/solution/`。这些观察都指向运行入口，不宜立即让 Codex 重写保存逻辑。

若添加可见但刷新丢失，先保留复现步骤，再给 Codex 一项能够区分原因的任务：

```text
同一浏览器、同一地址下，新增“示例网站”可见，刷新后消失。
请先检查新增时的数据写入与页面加载时的数据读取，
确认它们使用相同存储键，并检查是否有存储错误。
先解释证据指向哪里，再做最小修复。
修复后重跑新增→刷新→删除→刷新，不要顺便重做页面。
```

这段反馈把现象、稳定条件和下一项检查连在一起。它没有预先宣布根因一定是存储键；即使假设被推翻，也能沿实际结果调整。连续修改却没有新证据时，回到这个层次，比再加一句“务必正确”更有帮助。

## 动手练习：完成一次真实交付

现在请为自己的版本增加一个小改动：保存成功后清空标题与网址输入，列表保留新条目。先向 Codex 描述这个行为，再验证连续添加两条是否都成功。参考成品已有相应行为的读者，可以在副本中从起点完成，或只调查清空发生在保存成功之前还是之后。
