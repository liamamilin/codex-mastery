# 第 17 章：识别错误发生在什么层次

“Codex 说改好了，可我这里还是不行。”这句话很常见，也几乎没有给出调查方向。浏览器打不开、按钮没有反应、刷新后数据恢复，都可以被描述成“不行”，但它们需要的下一步完全不同。若一律回答“再修一下代码”，你可能在服务没有启动时改界面，在打开旧文件时重写逻辑，或者在需求没有说清时不断完善错误的结果。

本章要练的能力，是把一次失败缩小到一个能够检查的问题。完成时，你应能说出：目前确认了哪一段正常，哪个判断仍是假设，下一次检查会怎样改变行动。你不必先成为调试专家，但需要知道什么时候应该让 Codex 停止修改，开始调查。

## 先固定“在哪里发生了什么”

本章使用案例 D：Phantom Delete。它是独立的教学故障程序，数据与 LinkShelf 分开。准备现代浏览器、Python 3，以及教材文件。先阅读 `cases/D-phantom-delete/README.md` 的启动与数据边界；不要用真实收藏练习，也不要直接打开参考修复版。

在**教材仓库根目录的操作系统终端**执行：

```sh
python3 -m http.server 4176 --bind 127.0.0.1 --directory cases/D-phantom-delete
```

Windows 已安装 Python Launcher 时将 `python3` 换成 `py -3`。浏览器打开 `http://127.0.0.1:4176/starter/`，终端保持运行；结束时按 Ctrl+C。这里使用 Python 的本机静态服务，目录与绑定参数见 [Python 官方说明](https://docs.python.org/3/library/http.server.html)。如果尚未安装或检查 Python，回看[第 2 章](./02-工作环境.md)，先完成环境检查。

先记录完整地址、版本入口、点击对象和可见结果。例如：“在 `/starter/` 点击‘示例网站’的删除后，它从列表消失；不做其他操作，刷新同一地址，它又回来。”这里的每个限定都有用。省略“同一地址”，就可能混淆不同数据来源；省略“不做其他操作”，就可能漏掉另一动作已经保存了数据。

如果你已经练习过，点击“恢复初始样本”并确认，只重置当前版本的合成数据。不要为了得到整洁结果清空整个浏览器存储；那会破坏调查现场，也可能影响其他练习。

## 六个层次，对应六种检查

这些层次不是要填写的分类表。它们帮助你避免在没有证据时，把所有问题推给实现代码。下面的分支是**诊断示例**，不是声称本案例实际出现过全部故障。

| 不确定性所在 | 可以观察的分歧 | 能缩小范围的一次检查 |
| --- | --- | --- |
| 需求 | “删除”究竟只隐藏本页，还是刷新后也不恢复？ | 找到已约定的完成条件；若没约定，先补清楚。 |
| 环境 | 浏览器根本连不上地址。 | 检查服务终端是否仍在运行，端口与地址是否相同。 |
| 工具 | Codex 没有权限读取目标文件，却声称已经调查。 | 查看具体工具返回和实际路径，区分未执行与执行失败。 |
| 实现 | 点击后内存改变，存储未变。 | 追踪点击处理函数到保存函数，检查是否真的调用。 |
| 数据 | 两个地方都能读到数据，但读到不同的版本或来源。 | 核对浏览器、协议、主机、端口、专用键及记录 ID。 |
| 验证 | 只看见条目消失，就宣布持久删除成功。 | 追加同源刷新和再次读取，观察状态能否跨载入保留。 |

这六层可以相互影响。例如，写存储失败可能由浏览器策略造成，但程序若仍显示“保存成功”，还存在错误处理问题。你可以先确认环境拒绝这一事实，再决定是否要修正反馈。不要因为分类交叉就放弃调查；层次的价值是提出具体问题，而不是争论问题“究竟归哪一类”。

## 一次好检查，应让两个解释得到不同结果

面对“刷新后又回来”，可以提出两个候选解释：删除后的内存仍含原记录，只是页面把它藏起来；或者内存已正确删除，但保存没有发生。它们都能解释当前条目不可见，却预期不同的内存内容。

点击“检查内存与存储”。右侧会列出当前内存与重新读取的 localStorage 记录，包含 ID 和标题。若当前内存没有 `sample-1`，存储中仍有它，这就反对“只是隐藏页面，内存没变”这个解释，把注意力引向保存与读取之间。只比较数量还不够：两份列表都为两条，也可能各含不同记录，所以要核对 ID。

本案例的对照面板直接读取浏览器状态，不是预先编好的终端输出。但面板同样是程序的一部分：若其结果与外部观察矛盾，可以要求 Codex 引用 `shared/ui.mjs` 中 `inspect()` 的实现，再在浏览器站点存储面板独立核对专用键。验证工具也需要有可理解的来源。

你可以把下面这段发给 **Codex**：

```text
先不要修改。我在 Phantom Delete 的 starter 页面观察到：
删除 sample-1 后内存里没有它，但专用存储里仍有它；
刷新同一地址后它恢复。
请引用当前文件确认：点击事件调用什么、当前列表由谁持有、
保存函数在哪里、页面初始化从哪里读取。
把代码事实与仍待验证的推断分开。
下一步只提出一个最能区分原因的检查，并说明两种结果各意味着什么。
```

把其中的观察换成你真正看见的结果。若浏览器连不上，就不要复制“内存没有它”这句话，那会把不存在的事实塞进调查。此时下一步只是核对服务终端与 URL，而不是沿保存函数修改。

## 用文件把判断接到现实

Codex 的报告至少应该能连接到这条实际路径：`starter/app.mjs` 装配当前版本；`shared/ui.mjs` 将删除按钮接到 `deleteRecord()`；`starter/core.mjs` 决定删除后的列表；`shared/storage.mjs` 提供 `readRecords()` 与 `saveRecords()`。有了这条路径，你可以继续追问某一步，而不是接受“可能是缓存”的空泛解释。

同时核对数据身份。故障版使用 `codex-mastery:phantom-delete:starter:v1`，修复版使用另一个键。打开修复版后看见三条初始样本，不能证明故障版修复失败，因为它们本来就是独立数据。localStorage 按来源区分，`localhost` 与 `127.0.0.1` 也不是同一主机；相关行为与权限限制见 [MDN localStorage 文档](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)（核对于 2026-10-25）。

一个有用的阶段结论可以很短：

> 本轮已确认删除改变了内存，存储仍含原 ID。需要核对删除路径是否执行持久化；暂没有证据支持重写渲染。下一步检查 `deleteRecord()` 与 `saveRecords()` 的调用关系。

这比罗列十个可能原因更接近行动。它没有过早宣布根因，也没有把调查停在“需要更多信息”。

## 检查本身失败时，先保留边界

如果 Codex 的命令被权限拒绝，报告应写“未执行成功”，不能写“测试失败，所以代码有错”。如果 Node 测试通过，浏览器却打不开，要拆开两个结论：数据函数在测试输入下通过，当前 HTTP 入口尚未成立。测试通过不会启动服务器，服务器返回页面也不会证明保存逻辑正确。

如果你读到一份格式损坏的存储，先保留原值与专用键，再调查来源。把它清空后页面恢复，只能说明另一份初始数据可以运行，不能说明损坏原因已经修复。对真实项目，这种误判尤其昂贵：你可能用“恢复演示环境”代替了“修复用户数据路径”。

## 动手：为下一次行动写一句依据

在故障版完成一次“恢复样本→删除→检查→刷新”，保留自己的观察。让 Codex 提出两个不同层次的解释，你选一个能让两者产生不同结果的检查。执行后写三句：观察到了什么；哪个解释因此更可信或被削弱；下一步为什么该调查或修改某个具体位置。

再做一个迁移判断：如果页面完全无法连接，你原先那套删除检查还能执行吗？说出此时应先获取的证据，并实际核对服务终端与浏览器地址。完成标准是让下一步由证据决定，能够说明为何此时需要调查、修改、恢复环境或补充验收。下一章会沿已定位的数据路径完成最小修复。
