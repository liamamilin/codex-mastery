# 第 15 章：从“程序启动”到“功能真的可用”

你已经看见一个漂亮页面，终端没有红色报错，Codex 也说“完成”。现在试着回答：链接是否真的保存？搜索是否只显示匹配项？删除后刷新会不会回来？页面能够打开，只解决了访问入口，还没有回答这些问题。

本章把第 3 章的基础验收扩展成一组有针对性的行为检查。完成时，你会得到一份属于自己运行环境的验收记录，能指出哪些结论由自动检查支持，哪些由浏览器动作支持，还有哪些没做。重点是选择足以发现问题的动作，而不是增加测试数量。

## 从使用者的完成状态倒推

沿用案例 A 参考成品或自己的工作副本，准备 Python 3、浏览器。自动数据测试需要 Node.js 18+。运行方式见 `cases/A-linkshelf/README.md`，参考成品通常是 `http://localhost:4174/solution/`。保持同一浏览器和来源；端口或主机变化会让你读到另一份 localStorage。

先给“可用”一个具体定义：我添加“验收15·示例网站”，刷新后仍在；添加“验收15·学习资料”，搜索“验收15·学习”时只显示它；清空搜索恢复全部；删除指定条目并刷新，不会恢复；导出的 JSON 与当前列表对应。不要把“所有功能正常”作为记录，因为后来的人无法据此重复你的检查。

本章用专用标题前缀区分本轮样本；若已运行过本章，换一个新的前缀，只删除这次新增的记录。

保存这组动作时，同时写明前提。例如“首次空列表”和“已有两条收藏”是不同起点。已有重要收藏先导出备份，本轮只删除自己的测试条目。不要为了每次都从零开始，就清空整个浏览器数据。

## 四种检查，分别回答不同问题

| 检查 | 在这个案例里能回答 | 不能单独回答 |
| --- | --- | --- |
| 语法检查 | JavaScript 是否能被解析 | 按钮绑定是否正确、数据是否持久 |
| 数据逻辑测试 | 校验、筛选、读写函数面对指定输入的结果 | 浏览器 DOM、下载与焦点是否正确 |
| HTTP 与页面访问 | 入口和资源是否能从服务取到 | 新增、刷新和删除是否满足使用目标 |
| 浏览器行为验收 | 实际界面、刷新、键盘与下载行为 | 所有浏览器、所有输入与长期存储可靠性 |

在**仓库根目录的操作系统终端**执行：

```sh
node --check cases/A-linkshelf/solution/app.mjs
node --test cases/A-linkshelf/tests/core.test.mjs
```

本项目数据测试实际得到 10 项通过，涵盖保存后再次读取、删除后读取、坏协议、损坏数据、存储失败、搜索和 JSON。测试用程序化存储对象，不是真实浏览器权限面板。它给出了有价值的证据，也留下了明确边界。

若你的工作副本已改变函数或目录，不能把参考成品的测试结果直接贴到自己的交付里。让 Codex 说明测试实际导入的是哪份实现；路径不一致时，先对准目标再谈通过与否。

## 设计一条会暴露问题的路径

在浏览器中添加“验收15·示例网站” `https://example.com`。点击“保存到链接架”，记录列表与数量，然后刷新。接着添加“验收15·学习资料” `https://example.org/learn`，输入关键词“验收15·学习”，核对显示的是哪一个标题和网址，不能只记“显示一条”。清空搜索，应重新看见全部。

再删除“验收15·示例网站”，立即刷新。检查被删记录没有回来，另外一条仍在。这个动作同时防止两种误判：只更新当前 UI，却没保存删除；为了删一条，却清空了整份收藏。你检查的是目标变化与应保留的邻近数据。

最后点击“导出 JSON”，检查浏览器下载列表，并用文本编辑器打开实际文件。核对 `format` 为 `linkshelf`、`version` 为 1、`links` 中的标题与 URL 对应当前数据。不要只凭按下按钮或看见成功提示，就宣称文件已下载。此阶段没有导入，验收中不能补写“导入通过”。

案例 D 刻意保留了只删内存的版本，可以说明为什么刷新很关键：当前页面消失与跨刷新删除是两种结果。第 18 章会对这个差异做完整调查，本章先把这条边界写进验收，避免漏检。

## 错误输入与恢复，也属于使用路径

空标题保存，应该说明需要填写标题；网址输入 `example.com` 或 `javascript:alert(1)`，应该拒绝保存并说明接受的地址格式。检查数量未增加、已有收藏未变。随后改成合法值，应该可以继续新增。若错误后整个表单再也不能用，单独一条“错误输入被拒绝”的测试仍漏掉了恢复问题。

存储失败是另一个边界。自动测试用会抛错的存储对象检验反馈与数据保护；若你要在浏览器核对，先备份测试数据，再按该浏览器的站点存储设置操作。入口和行为因浏览器而异，没有执行就写“浏览器权限场景未测”，不要把测试对象的成功当作真实设置已验证。

键盘也做一次最小检查：用 Tab 移动到标题、地址与按钮，确认焦点看得见；表单内按 Enter 提交；错误时能找到要修改的字段。在窄屏中观察输入和列表是否可读、有无横向溢出。测试无需遍历所有分辨率，但你应该记录实际看过的尺寸与浏览器。

## 让 Codex 为结果负责，而非为数量负责

把下面的任务发给 Codex，并根据当前可用工具调整：

```text
请按实际使用行为检查 LinkShelf：新增→刷新、搜索→清空、
删除指定项→刷新、坏网址→修正、导出→读取实际文件。
每项写出起始数据、动作与观察；说明检查针对哪份代码。
能运行的检查实际运行，没有浏览器就保留人工步骤与未验状态。
出现失败先保存复现条件，不要为了让测试通过改掉完成条件。
```

好的回复会指出某个动作和结果，例如“删除编号对应条目后再次读取未出现，另一条仍在”。“执行 50 项测试，全绿”若没有说明覆盖什么，仍不足以支持当前目标。反过来，一个能稳定暴露删除恢复的检查，可能比许多只验证函数存在的测试更有价值。

## 失败之后，只扩大必要范围

如果搜索返回错误条目，先保留输入和预期，定位筛选与渲染之间的差异；修复后重做搜索、清空和新增后可见性。若删除影响了保存路径，重做新增、删除、刷新与写入失败。不是每次都需要重跑所有工具，也不能因为刚修过一个点，就跳过受影响的相邻路径。

检查无效时还要质疑验证方式。两个测试若都从同一个错误计算取预期值，只是互相附和；浏览器若打开的是旧服务目录，重试再多次也没在验证新实现。记录完整 URL、实际文件与命令退出状态，往往比增加重试次数更有帮助。

## 动手：完成自己的验收记录

亲自完成上面的使用路径，保留一份短记录：环境与目标版本；动作及结果；失败与修复后的复测；尚未执行的范围。挑一项，让另一位读者只凭记录重复，看看是否还缺起始条件。

完成标准不是一张全部勾选的表，而是你能解释每个“通过”来自哪种观察，以及哪个重要边界还没有证据。后续交付时，这些可重复的行为会比一句“我这里能跑”更有用。
