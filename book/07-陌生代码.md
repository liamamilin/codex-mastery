# 第 7 章：接手一份你不熟悉的代码

“帮我给这个工具加一个筛选。”如果这是你昨天写的项目，你可能知道从哪里动手；如果它来自别人，第一件难事往往是判断：到底运行哪个文件，改动会碰到什么，已有测试能证明多少？此时急着写代码，可能把原有能力重新做一遍，却漏掉真正的入口。

本章使用新的案例 TaskTrail，一个离线的 Python 任务清单。你不需要先学会 Python。完成时，你应拿到一份简短事实简报：入口在哪里、数据从哪里读取、怎样运行测试、目前确认了什么，以及增加状态筛选之前还缺哪项信息。本章暂不实施筛选。

## 给陌生项目一块独立的工作位置

沿用第 2 章的 Codex 与终端准备，另需 Python 3.9 或更新版本。程序只用标准库，即 Python 自带模块，不需要安装第三方包。它把任务保存为 JSON，一种用字段与列表组织数据的文本格式，你可以用普通编辑器查看。案例起点在教材根目录的 `cases/B-tasktrail/starter/`。先不要打开 `solution/`；那是改完以后的参考成品，会干扰你判断起点到底具备什么。

在文件管理器确认教材根目录中**尚无 `my-tasktrail`**；已有同名目录时选新名称，并替换后文路径。

**macOS / Linux，在教材根目录的操作系统终端：**

```sh
cp -R cases/B-tasktrail/starter my-tasktrail
cd my-tasktrail
python3 --version
codex --sandbox read-only
```

**Windows PowerShell，在教材根目录：**

```powershell
Copy-Item -Recurse cases/B-tasktrail/starter my-tasktrail
Set-Location my-tasktrail
py -3 --version
codex --sandbox read-only
```

Windows 没有 `py`、但 `python --version` 返回 Python 3 时，后面的 `py -3` 可换成 `python`。若上一章采用 `codex.cmd` 解决 PowerShell 脚本策略问题，继续使用同一入口。复制的是起点文件，不能借此覆盖自己以前的任务清单。

## 先要一份能核对的简报

下面发给 **Codex 输入框**：

```text
我接手了当前目录的 TaskTrail，准备给列表增加按状态筛选。
先只读调查，不修改源码、样本或说明，不安装依赖。
不要读取教材中的 solution 参考成品。
请从目录与 README 开始，定位：
1. 实际命令入口，以及列表、添加、完成各走到哪里；
2. 数据文件怎样选定，相对路径从哪里计算；
3. 测试怎样运行，会不会写入项目文件。
用文件路径支持结论，区分代码事实、运行证据与未确认项。
若一项检查会写入文件，先给出命令与影响，暂不执行。
```

“先调查”不是要求它画一张庞大架构图，而是暂时把学习目标从改功能换成找事实。入口、数据与测试这三条线，足以支撑这个小项目的下一步。工具若因权限拒绝而没能读取，也要保留这个区别：没有读到，不等于文件不存在。

收到简报后，挑一条最有影响的结论亲自检查。例如它说“任务保存在 JSON 中”，这仍太宽。你需要知道本次命令会使用哪一个 JSON、缺少文件时会怎样、运行命令的位置是否影响解析。让它引用处理参数与读取文件的代码，而不是依据 README 的一句话补全整个实现。

## 用运行结果补上第二层证据

打开另一个终端，进入你刚复制的 **`my-tasktrail` 目录**。这次由你运行命令，不把命令粘到 Codex 的自然语言输入框：

```sh
# macOS / Linux；Windows 把 python3 换成 py -3
python3 -B tasktrail.py --help
python3 -B tasktrail.py --data sample.json list
python3 -B -m unittest discover -s tests -v
```

`-B` 禁止 Python 生成字节码缓存，便于保持项目目录清楚；它不禁止程序保存任务。最后一条运行 `tests` 目录中的单元测试。测试会在系统临时目录创建、清理自己的数据，因而不是“全电脑绝不写文件”，但不会用样本文件试写任务。若你的执行环境禁止临时写入，记录这个限制，不要把权限失败解释为业务功能失败。

原始样本的预期列表包含 `[ ] #1 核对入口命令` 和 `[x] #2 阅读项目说明`。方括号表示状态，编号用于定位任务。四项测试应通过；如果你已经改过副本，结果以当前文件为准，不强行套用起点记录。制作时实际执行的环境与命令保存在[案例 B 运行说明](https://github.com/liamamilin/codex-mastery/tree/main/cases/B-tasktrail)，这是参考项目的证据，不会自动变成你电脑上的通过记录。

尤其要核对 `--data`。它是必须显式提供的参数，放在 `list`、`add`、`done` 等子命令之前；`sample.json` 相对于终端当前目录，而不是相对于脚本所在位置。因此，从另一个目录调用脚本时，同样的短文件名可能指向另一份数据。先固定工作目录，比遇到空列表后立即修改读取函数更有效。

## 让简报保留不知道的部分

现在请 Codex根据你的真实输出补充调查结论。可以发：“我在副本目录运行了以上命令，得到以下输出。请判断它们增加了哪些证据，不修改程序。”只粘贴与问题有关的结果，不需要附上整个终端历史。

一份够用的简报可以有五行：入口；数据路径规则；核心文件职责；实际检查；下一项未知。比如“测试通过”应跟着具体命令与范围，“还没实现状态筛选”应由当前帮助与代码支持。不要让它把参考成品有的功能写到起点上。README 不完整，也不意味着说明在撒谎；程序、测试与说明各自提供一部分信息。

原有测试通过，只能说明它覆盖的已有行为符合预期。它没有预先证明未来的筛选正确，更不能证明对任意数据都安全。你可以要求它指出“哪一个现有测试对本次修改最有约束”，再说明还要增加什么断言。断言就是测试中对结果作出的具体要求，例如只显示未完成，而已完成的编号不应出现。

## 遇到陌生报错，先判断发生在哪一层

如果终端说找不到 `tasktrail.py`，先检查是否进入副本目录；如果参数解析提示缺少 `--data`，先补齐调用方式；如果提示数据格式异常，先保留并查看指定文件，不要删除所有 JSON。三种失败分别来自入口、参数与数据，不能用“程序坏了”一概代替。

还有一种偏差来自 Codex：它读完 README 就开始重构。此时明确纠正：“当前终点是事实简报。先停止修改，引用入口和数据路径；实施留到下一章。”若已经改动，先检查实际差异，再只撤回此次误改。用新副本练习的好处，是调查对象足够清楚，不会与真实项目的旧改动混在一起。

## 动手练习：发现一条说明没有写透的边界

在不改实现的前提下，请 Codex从测试或代码中找一条 README 没有详细说明的输入边界。让它指出：什么输入触发、程序怎样反馈、原数据会不会改变。随后用系统临时目录或副本中的新数据文件验证，**不要对 `sample.json` 做写入实验**。执行前先确认会创建什么文件；需要写入时，由你在终端运行，或在明确授权的工作区写入会话中运行。
