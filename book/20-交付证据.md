# 第 20 章：他说完成了，但你怎么确定？

“已完成，所有检查通过。”这句话可能意味着文件已经写入，也可能意味着服务终于启动。等你真正删除一条收藏，刷新以后它又回来。问题不只是检查做得少，而是交付结论超出了证据能支持的范围。

[第 5 章](./05-完成状态.md)讨论开工前怎样确定终点。本章站在交付时刻：面对已经产生的文件、日志、测试和界面，怎样判断现在能交付什么，还缺什么。完成后，你应能写出一份简短、有实际依据的交付说明，也能识别“程序运行了”与“问题修好了”之间的缺口。

## 五种状态，不是一张统一通行证

先把常被混用的状态拆开。

| 状态 | 需要看到的证据 | 单独还不能证明 |
| --- | --- | --- |
| 已写 | 实际文件与对应差异 | 语法正确或功能存在 |
| 已构建 | 该版本构建命令成功、产物确实生成 | 关键操作按目标正确 |
| 已运行 | 正确版本启动、入口可访问 | 删除后刷新不会恢复 |
| 按目标验收 | 约定输入与操作下，实际结果符合要求 | 所有平台、所有场景均正确 |
| 可继续维护 | 别人能定位变更、运行检查、理解限制和下一步 | 永远不会出现新问题 |

它们不是每个项目都必须依次盖章的五个门禁。案例 A、D 是原生静态文件，没有必要为了写“已构建”额外增加打包工具。可以记录“不需要构建；模块语法与实际运行分别检查”。教材阅读站需要静态构建，那是另一个产物的证据，不能代替案例行为验收。

同样，不要求每轮同时证明整套产品永远可维护。当前改动的入口、原因、测试与限制能被下一位操作者理解，就已经比只有一句“完成”更可接续。

## 用两个案例看清证据错位

LinkShelf 的数据测试位于 `cases/A-linkshelf/tests/core.test.mjs`。它检查读写、校验、搜索和导出格式，包括删除最后一条后重新读取为空。测试使用程序化存储对象，能快速验证数据逻辑，但没有点击真实按钮，也没有证明浏览器已下载文件。

Phantom Delete 更容易暴露误解。它的测试同时导入 `starter` 与 `solution`：一个用例要求成功复现“内存删除、存储仍有记录”，另一个用例要求修复版的删除确实写回。因此，故障版相关用例通过，说明教学故障按设计存在，绝不意味着故障版已经可当作修复交付。

检查测试名称与断言，才能知道绿色结果的含义。看到测试总数和通过率，却不知道它检查的是哪个版本、哪个行为，仍不足以作出交付决定。若你修改的是 `my-phantom-delete`，而运行的测试导入教材的 `solution`，即使全部通过，也还没有检查你的修改。

## 先把“对象”和“证据”接起来

审视一份交付时，先找到实际产物。它是哪个目录、哪个入口、哪组修改？然后找支持它的命令与观察。最后再读结论，检查是否有跨越。

例如，“本机打开参考修复版”需要指向 D 的 `/solution/`；“检查我的修复”则需要指向工作副本的 `/starter/`。浏览器标签页看起来相似，不能省略版本确认。D 的两个原始版本使用独立存储键，切换后看到三条样本，也不能立刻判为上一版本的删除失效。

一次证据链可以很短：目标是删除后不恢复；变更位于删除保存路径；数据检查在目标版本通过；浏览器按固定顺序复现与回归；交付保留启动方法和未覆盖条件。每一环都回答上一环留下的问题，而不是堆积无关输出。

## 实际执行一条足够聚焦的检查

在**教材根目录的操作系统终端**运行：

```sh
node --test cases/A-linkshelf/tests/core.test.mjs cases/D-phantom-delete/tests/delete.test.mjs
```

需要 Node.js 18 或更新版本，无需联网安装依赖。编写本章时在 Node.js `22.21.1` 实际执行，**19 个测试通过、0 个失败**。其中 A 为 10 个，D 为 9 个；D 包含对故意故障的复现断言。这个结果只对应当时的教材文件和数据层检查，不能给未来修改或工作副本自动背书。

还实际对 D 的 `starter/core.mjs`、`solution/core.mjs`、`shared/ui.mjs` 运行过 `node --check`，语法检查通过。它没有执行浏览器中的 DOM 事件，不应被写成“页面交互全部通过”。浏览器与移动端的集成验收需另有实际记录；当前最新范围以案例 README 和仓库 `progress.md` 为准。

如果只想复核 D，可以单独运行 `node --test cases/D-phantom-delete/tests/delete.test.mjs`。这有利于看清故障与修复的不同断言。测试失败时保留完整错误和执行目录，先判断目标文件与输入条件是否正确，再修改实现或测试。

## 浏览器证据为什么还需要动作顺序

D 故障版的新增，会保存当前完整内存数组。因此“删除一条→新增另一条→刷新”可能顺便把前次删除保存下来，掩盖原来的缺口。若交付记录只写“我试过删除和新增”，就无法知道关键故障是否真的被检查。

检查修复版或自己的工作副本时，先确认版本，恢复合成样本，再执行：删除“示例网站”→检查内存与存储都为两条→直接刷新→确认被删记录不再出现，另外两条保留。先不要混入新增。随后再单独新增并刷新，检查相邻功能；删除至空列表后刷新，确认没有重新播种。

按案例 README 在本机启动即可：教材根目录运行 `python3 -m http.server 4176 --bind 127.0.0.1 --directory cases/D-phantom-delete`，浏览器打开 `http://127.0.0.1:4176/solution/`。Windows 换用 `py -3`；停止时在服务终端按 Ctrl+C。检查自己的修复时将目录参数换成 `my-phantom-delete`，访问 `/starter/`，保持同一来源。

这些是可复现操作，不是本段已经替你执行的浏览器日志。亲自观察后，写下结果；出现差异则保留数据和动作，回到[第 18 章](./18-停止无效修补.md)检查原因。不要为了得到符合预期的截图，先清除证据。

## 交付说明只保留能帮助复查的内容

可以请 Codex 汇总：“实际改了哪里、怎样运行、执行了哪些检查、每项支持什么结论、哪些仍未验证。”不需要附上所有思考和每次列目录的输出。读者需要的是可定位的产物和证据。

下面是一份**填写示例**，并非你的工作副本已经通过的证明：

```text
产物：my-phantom-delete/starter/core.mjs 中的删除保存修复。
变化：删除后的新数组先保存，成功后再返回给界面；保留专用键与校验。
数据检查：填写实际针对此副本执行的命令和结果；未执行就写待验。
浏览器：填写版本地址、删除→检查→直接刷新及相邻回归的真实结果。
运行：从教材根目录按本案例 README 的工作副本命令启动。
限制：合成练习数据；未检查的系统或权限场景明确列出。
下一步：若浏览器待验，先完成该动作，再决定是否达到本轮终点。
```

“可维护”也落在这些内容里。下一位操作者能够知道为什么加这一行、保存失败时怎样处理、测试在哪，才有机会继续。如果只留下大篇赞语，没有入口和差异说明，维护者仍需重新调查。

## 动手练习：识别一次虚假的完成感

下面是**教学模拟交付**：“已彻底修好删除。Python 服务启动正常，首页返回 200，Node 测试全绿。页面截图很美观，功能全部完成。”补充事实：测试导入参考 `solution`，实际修改在工作副本；截图只显示初始三条样本，没有记录删除或刷新。

请写一段不超过五句话的回复，指出当前能确认什么、不能确认什么，以及最小补充检查。不要要求把所有功能重新开发一遍。
