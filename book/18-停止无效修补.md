# 第 18 章：停止无效修补，重新检查假设

你让 Codex 调整了列表显示，删除后刷新仍会恢复；再让它重新渲染，结果依旧。下一次它建议“等一会儿再刷新”。这段修补过程是**教学示意情境**，并非本项目实际发生的对话记录。它描述了一种熟悉的失控：每轮都有改动，却没有新增能够解释失败的证据。

真正需要停止的是没有依据的重复修改。一次尝试若已经反对了原先解释，就可以立即转向调查；不必等到固定的第三次。本章使用可运行的 Phantom Delete 故障代码，练习把任务从“再修一下”改成“重新检查假设”，最后得到能解释、能刷新验证的修复。

## 保留故障，建立自己的修复副本

沿用[上一章](./17-错误层次.md)的 Python 3、浏览器与案例 D。另需 Node.js 18 或以上版本运行数据逻辑测试；没有 Node 仍可做浏览器练习，但不能声称自动测试已经通过。先确认仓库根目录没有同名 `my-phantom-delete`，已有时换一个新名字。

在**仓库根目录的操作系统终端**复制整个案例。macOS / Linux：

```sh
cp -R cases/D-phantom-delete my-phantom-delete
```

Windows PowerShell：

```powershell
Copy-Item -Recurse cases/D-phantom-delete my-phantom-delete
```

连同 `shared/` 一起复制，因为两个版本共用 UI 与存储模块。让 Codex 在副本中工作，只修改 `starter/core.mjs`；先不读 `solution/`。停止原先 4176 服务，再从仓库根目录运行副本：

```sh
python3 -m http.server 4176 --bind 127.0.0.1 --directory my-phantom-delete
```

Windows 将 `python3` 换成 `py -3`。浏览器打开 `http://127.0.0.1:4176/starter/`，结束时在服务终端按 Ctrl+C。不同浏览器或来源会看到不同存储；练习保持同一个浏览器、地址与操作页。

副本只隔离文件。同来源、同版本的副本与原件仍可能共用本案例键；请仅使用合成样本，需要保留的调查结果先备份，再恢复初始状态。

## 先复现一次，期间不要做别的动作

点击“恢复初始样本”并确认，看到三条合成链接。删除“示例网站”，点击“检查内存与存储”，然后直接刷新。故障版的预期是：删除后当前内存只剩两条，存储重新读取仍有三条；刷新后三条恢复。你要亲自记录这个结果，而不是照抄为已执行日志。

![Phantom Delete 的真实运行界面：在同一屏对照当前内存与重新读取的存储](./public/screenshots/phantom-delete.jpg)

图中界面用于说明观察位置；你的数据与操作结果以自己的运行记录为准。右侧是真实浏览器状态的对照，不是网站替你运行了 Codex。

这里有一个会掩盖证据的分支：**删除后先新增，可能使故障暂时消失**。新增会保存当前完整内存数组，也就顺带保存了此前的删除。因此第一轮必须是“重置→删除→检查→直接刷新”。稳定复现依赖具体动作顺序，笼统的“有时删除有问题”会把这个差异藏起来。

## 把一个猜测拆成有方向的数据路径

“刷新后回来”只说明跨刷新状态不一致，单凭现象还不能排除读错键、错误初始样本或写入被拒绝。先让 Codex 沿路径调查。发给 **Codex**：

```text
先不修改。副本的 starter 删除 sample-1 后，内存没有它，
重新读取存储仍有它，刷新后恢复。
请沿点击事件→内存列表→存储写入→初始化读取追踪，
引用真实文件和函数。区分已确认事实与假设。
提出一个最小检查：它的不同结果分别支持什么解释？
不要先添加重渲染、延时或另一个缓存。
```

实际入口 `starter/app.mjs` 把当前版本的 `deleteRecord()` 交给 `mountLab()`。在 `shared/ui.mjs` 中，删除按钮执行删除函数，把返回数组赋给当前 `records`，再调用 `render()`。刷新初始化时，`readRecords()` 从当前专用键重新读取，只有键不存在才创建样本。空数组不会自动变回三条。

![刷新前后的数据路径：新列表必须保存，刷新才会重新读到它](./public/diagrams/storage-path.svg)

再看副本的 `starter/core.mjs`。这里是真实代码结构：

```js
export function deleteRecord(storage, key, records, id) {
  const next = records.filter((record) => record.id !== id);
  return next;
}
```

它生成新数组，却没有调用已导入的 `saveRecords()`。这与“内存两条，存储三条”相互支持：删除被执行了，缺少的是把新状态留下。当前页面已经正确消失，再调用一次渲染并不会改写存储；等更久同样不会凭空产生一次写入。

最小检查可以直接对照同一 `sample-1`：删除后它是否仍在专用键中？本页“检查内存与存储”提供这次再次读取；开发者工具的站点存储面板可提供独立观察。检查记录 ID，不能只看数量。若存储也已不含它，但刷新仍恢复，就应继续查实际读取来源，不能套用本章这一行修复。

## 最小改动，还要守住失败时的行为

让 Codex 只补全缺失路径：

```text
现有证据支持删除结果未写回存储。
只在删除函数返回新数组前调用已有 saveRecords(storage, key, next)。
不要增加定时器或重写 UI。检查此前有无无关补丁，
只撤回本次练习中确认无用的改动，不覆盖我其他修改。
写入失败时保留原列表并报告失败，不能显示持久删除成功。
完成后给出 diff，以及你实际执行和仍待人工执行的检查。
```

对应的最小差异为：

```diff
   const next = records.filter((record) => record.id !== id);
+  saveRecords(storage, key, next);
   return next;
```

保存发生在返回之前。调用方只有等函数正常返回才替换 `records`；若保存抛出错误，赋值未完成，UI 捕获错误并保持原列表。这条顺序让“未保存”成为可见失败，避免又出现只改当前页面的假成功。不能用“捕获所有错误后继续返回新数组”把写失败吞掉。

参考修复在 `solution/core.mjs`。对照时重点看这条因果链，不要因为参考文件更短，就用整目录替换自己的工作。你可能已经加入有效的说明或检查，它们不应随着无关补丁一起丢失。

在真正动手前，还可以把预期写成一个很小的实验：“如果遗漏写入是原因，补上这一行之后，删除后的存储应立即不再含原 ID；不必等刷新才知道。”这样修复不再只是编辑动作，而是一次会产生明确结果的判断。若存储依旧不变，就检查新代码是否加载、调用是否到达、异常是否发生，不能在没有区分这些情况时继续叠加第二个补丁。

## 修复后的检查，需要跨过同一条边界

在副本故障入口中重新恢复样本。删除“示例网站”，检查两份状态都不含 `sample-1`，然后刷新，确认它不再回来。仅观察删除后消失，仍是最初那个不足的验收。接着保留另外两条，新增“回归检查” `https://example.com/check`，刷新后确认新条目留下、被删条目没有恢复。

再逐条删到空列表，刷新后应仍为空。这能区分“删除保存正确”与“初始化把空列表当成从未开始”。最后输入坏网址，确认报错而不污染已有记录，再改成合法网址检查新增可继续。回归不必穷举整个应用，但应覆盖同一保存路径与相邻边界。

原案例的自动检查在**仓库根目录**执行：

```sh
node --test cases/D-phantom-delete/tests/delete.test.mjs
```

本项目在 macOS 26.6.2、Node.js v22.21.1 上实际执行，9 项通过：其中故障测试刻意确认 starter 删除后存储仍含原 ID，修复测试则要求再次读取不恢复；还覆盖最后一项删除、新增回归、写入抛错与重置隔离。故障测试通过，表示故障可复现，不能把它说成 starter 通过了产品验收。

原测试固定检查原案例两种版本。你修改工作副本后，不要拿原案例测试通过当作副本证据。可让 Codex 在副本另写一条回归检查：准备存储→调用自己的删除函数→再次读取→断言原 ID 不存在；再实际执行。浏览器点击、焦点与刷新另按上述流程观察，函数测试不替代这些步骤。

## 什么时候应改变路线

如果修复后遇到浏览器拒绝存储，继续加保存调用也没有用。保留失败信息，核对当前来源与权限；若当前环境无法满足持久保存，就明确标注未验范围，换可用浏览器或调整练习条件。若存储已正确、刷新却读错来源，沿读取路径继续取证。下一步必须由新证据决定，而不是维护最早的猜测。

本章不要求你背下 JavaScript，而是能要求 Codex 解释：什么被改变、什么被保存、刷新又从哪里读取。不断追加“务必认真”不能替代这个因果关系。让每轮尝试得到新信息，即使要几轮，也是在推进；如果补丁无法说明预期会改变哪次观察，就应先停下来。

## 动手：交付一次能被复查的纠偏

保留你的工作副本，完成一次调查与最小修复。给后来接手的人留一段简短记录：复现动作与原观察；被证据削弱的解释；实际修改的函数；删除→刷新与新增→刷新的真实结果；尚未执行的检查。对话若由你设计，用“示意”标明，不能填成真实工具日志。

完成标准是你能解释为什么原先的渲染或延时补丁无效，并用跨刷新的结果证明新的行动触及了真正路径。这种能力可以迁移到文件未写盘、配置被旧值覆盖、导出只存在内存等任务：先找到状态跨越边界的位置，再决定该修哪一步。
