# 第 11 章：用最小实验处理关键不确定性

一份报告写得很流畅，总访问数却算进了重复行。继续让 Codex“优化分析”，可能只是让错误多出几段解释。最值得先做的，有时不是完整报告，而是一个小到能够手算、又能区分两种处理方式的输入。

本章用案例 C：CSV Insight。你会明确一个假设，用四条记录做实验，根据结果决定是否扩大输入。最后应有一份实际生成的小报告、一个独立核对结果，以及继续或调整的理由。这里运行的是离线 Python 程序，不是网页自动调用 Codex。

## 让实验只回答一个关键问题

CSV 是按行保存表格的文本格式。这个案例使用 `date,channel,visits,signups` 四列，分别表示日期、渠道、访问数与注册数。数据是人工样本，不能写成真实业务表现。本次先问：“按明确约定排除空值与完全重复后，总数能否与手算一致，并说明哪些行被排除？”

约定是：任一必需字段为空，就排除整行并说明；四字段去首尾空格、将数值解析为整数后完全相同，只计第一条。日期相同、渠道相同而数值不同，仍保留。它是一种已选口径，不是所有数据都应遵守的规则。真实工作中若重复行的含义未知，要先问数据提供者，不能用“常见做法”悄悄替他决定。

实验需要同时包含能触发分歧的输入。只有正常数字，程序不管怎样处理空值都可能通过；只有一条记录，也看不出是否去重。四条数据就足以让这两个假设暴露差别，不必先制作几万行数据或一个仪表盘。

## 把案例复制到自己的练习位置

需要 Python 3.9 或更新版本，无第三方依赖。先确认教材根目录中没有 `my-csv-insight`，再执行：

```sh
# macOS / Linux；在教材根目录
cp -R cases/C-csv-insight my-csv-insight
cd my-csv-insight
python3 --version
```

```powershell
# Windows PowerShell；在教材根目录
Copy-Item -Recurse cases/C-csv-insight my-csv-insight
Set-Location my-csv-insight
py -3 --version
```

Windows 没有 `py`、但 `python --version` 返回 Python 3 时，可用 `python`。已有同名目录就换一个新名称，不覆盖旧报告。案例提供可运行的参考脚本；你先验证它的关键行为，再决定如何复用。若选择让 Codex自己实现，同一份小输入也可用于实施前约定验收，而不是假称参考代码是它刚刚独立写出的。

打开 `input/probe.csv`，应看到：

```csv
date,channel,visits,signups
2026-10-01,search,10,1
2026-10-01,search,10,1
2026-10-01,newsletter,8,2
2026-10-01,community,,1
```

先别运行，在纸上计算。第二条与第一条完全重复，只计一次；最后一条访问数为空，整条排除。因此访问应为 `10 + 8 = 18`，注册应为 `1 + 2 = 3`，计入两条。表头不是数据记录，行号仍从文件第一行开始。

## 给 Codex 一个带判断条件的实验

在 **`my-csv-insight` 副本**中打开 Codex，允许它读取输入并写入 `output/`，然后发送：

```text
先用 input/probe.csv 验证统计口径，不改实现与原始样本。
空值整行排除，完全重复只计首条，并报告原行号。
预期访问18、注册3、计入2、空值排除1、重复排除1。
请先读取相关脚本，再生成 output/probe-summary.md，
使用 verify_totals.py 独立核对。
若结果不符，先解释是哪项输入或规则导致差异，不扩大到完整报告。
```

你也可以自己在**副本根目录的操作系统终端**运行：

```sh
# macOS / Linux；Windows 将 python3 换成 py -3
python3 -B report.py --input input/probe.csv --output output/probe-summary.md
python3 -B verify_totals.py --input input/probe.csv --report output/probe-summary.md
```

命令会创建或替换指定报告，因而不是只读操作。路径以终端当前目录为起点。`-B` 只避免字节码缓存，不关闭报告写入。打开 Markdown 看总数、排除行号和说明，再比较核对程序的退出结果。能生成文件，只支持“写出了产物”；数字与已约定规则一致，才支持这个实验通过。

## 独立核对怎样增加证据

`verify_totals.py` 不导入报告模块，而是重新读取 CSV，以集合和列求和计算，再与报告正文总数和核对 JSON 比较。两条代码路径降低同一个实现错误被重复引用的机会；它们仍使用同一口径，不能证明口径本身适合真实业务。手算的四条样本提供了第三个容易理解的参照。

制作时，这两条小实验命令已实际得到访问 18、注册 3，独立核对通过。完整样本也已生成并核对，计入 21 条，访问 2155、注册 267；详细环境和未验证范围在[案例 C](https://github.com/liamamilin/codex-mastery/tree/main/cases/C-csv-insight)。这些是参考项目的执行记录，你的副本仍要亲自运行。

如果报告数字对了却没有解释排除记录，实验仍没有满足完整条件。若数字不同，先比较是否计了重复、是否把空值当零、是否跑错文件。不要立即扩大样本或重写整个工具；扩大输入会让原因更难辨认。

实验开始前也要写下结束条件：本次只判断既定规则能否产生可核对总数，不制作界面，不研究部署。数值与行号一致，就保留输入、命令和结论，进入完整样本；若发现规则本身含糊，就停在这个决定上，先澄清口径。一次失败若指出了关键假设，也已经提供价值，不需要为了把实验写成成功而偷偷换数据。

## 通过后再扩大，失败后改变问题

小实验通过，才用同一副本运行完整输入：

```sh
python3 -B report.py --input input/activity.csv --output output/summary.md
python3 -B verify_totals.py --input input/activity.csv --report output/summary.md
python3 -B -m unittest discover -s tests -v
```

完整输入有 24 条记录，其中两条空值、一条完全重复；报告应说明 21 条计入，而非默默丢掉三条。四项测试还检查重复运行得到相同字节、坏数值不覆盖已有报告等行为。看到失败时，保留错误与旧文件的区别：旧报告存在，不等于本次新输入已处理成功。

接下来若想验证“改一条输入是否会反映到输出”，选择一条非重复记录，例如 `newsletter,80,16`，在另一个输入副本中把访问改成 87，再生成另一个输出。按当前样本，访问应增加 7、注册不变。不要改重复对中的一条来做这个实验，否则去重关系也会变化，无法只观察数值增量。现有自动测试已经在临时数据上实际检查了这一变化。

## 动手练习：写一句实验结论

将自己的观察写成三句话：验证了什么假设；结果是什么；据此继续哪一步。再加一句未覆盖范围，例如“没有确认真实业务中重复行的含义”。不要写“所有数据都没问题”。
