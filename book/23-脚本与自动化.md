# 第 23 章：把重复操作变成脚本与自动化

你已经让 Codex 生成过一次 CSV 报告。下周换一份同格式数据，如果还要重新请模型计算每个总数，就把本来可以固定的工作交回了不确定的过程。更合适的分工是：让 Codex 帮你制定、维护和解释方法，让程序执行明确的读取、统计和核对。

本章从案例 C 的两条命令出发，形成一条可重复运行的本地任务。完成时，你会确认相同输入是否得到相同结果，坏输入是否停止，以及结果文件在失败后应如何解释。调度属于下一步选择，本章不替你创建定时任务或外部发送流程。

## 先把重复的边界圈出来

准备 Python 3 与完整案例 C，不需要 pip、网络服务或模型 API。先读案例 README，确认四字段、空值排除、完全重复只计首条，以及非法日期或数值使整次失败的约定。自动化一个尚未确定的口径，只会更快地重复错误。

当前稳定部分是：读取一个指定 CSV，生成一个指定 Markdown，再用独立脚本核对。需要判断的部分是：新数据是否仍符合定义，排除记录是否合理，数值支持怎样的结论。不要把“脚本返回成功”扩展成“业务判断正确”。

在**案例 C 目录**，基础动作仍是：

```sh
python3 -B report.py --input input/activity.csv --output output/summary.md
python3 -B verify_totals.py --input input/activity.csv --report output/summary.md
```

Windows 将 `python3` 换成 `py -3`。第二条命令必须核对第一条的同一输入与输出，不能不小心检查上次报告。运行前确认哪些旧结果需要保留，另选练习路径，不把唯一一份业务报告当作试验材料。

## 把顺序与失败规则交给小脚本

本项目提供 `extensions/run-csv-report.py`，只封装已有流程：用当前 Python 执行 `report.py`；成功才执行 `verify_totals.py`；任一步非零退出就停止。它没有复制统计逻辑，也没有在运行时调用模型。

在**教材仓库根目录**执行，输出选择一个新的练习位置：

```sh
python3 -B extensions/run-csv-report.py --input cases/C-csv-insight/input/activity.csv --output my-reports/summary.md
```

Windows 对应为：

```powershell
py -3 -B extensions/run-csv-report.py --input cases/C-csv-insight/input/activity.csv --output my-reports/summary.md
```

如果已有同名文件且你想保留，先改输出名。包装脚本从自身位置找到案例实现，将输入输出解析为实际路径，因此不用先切入案例目录；两条子命令使用相同解释器和文件。它以参数列表启动程序，不把输入文件名拼进任意 shell 代码。

预期先看见生成结果，再看见独立核对通过。对完整样本，访问 2155、注册 267，计入 21 条，空值 2 条、重复 1 条。最后的完成提示只表示本地生成与核对结束，没有上传、发消息或安装调度器。

## 实际运行两次，比较的是文件

保持输入和口径不变，执行同一条包装命令两次。第一次后把报告另存一份，再用编辑器比较两份文本，或让 Codex 比较字节与 SHA-256。不能只因为两次终端都说成功，就推出内容完全一致。

本项目在 macOS、Python 3.10.13 的系统临时目录中实际执行两次，独立核对均通过，输出字节相同，SHA-256 为：

```text
1f324ecf2250998285cd71b57aeda07cd67ce1281c3d386485b9c41c03b11c12
```

这证明当前样本与实现的这次重复结果。它不是所有未来输入都正确的证明，也不要求你在改数据后还得到同一个哈希。报告刻意不加入每次变化的时间戳，让相同输入的差异更容易判断。

再在自己的输入副本改一条非重复记录，保持注册不变，把访问增加 7。若其它口径不受影响，报告总访问应增加 7。不要改重复对中的一条：那会改变去重关系，结果不再只是数值加 7。输入扰动能检查脚本是否真读了新数据，而不是不断返回固定答案。

## 失败时，旧文件仍在不等于本次成功

在临时输入中把访问数改成 `no-number`，保留原报告再运行。预期生成失败、退出码非零、旧报告字节不变，包装脚本不继续报告独立核对成功。本项目实际执行了这条分支，得到退出码 2，旧内容保留。

保护旧文件有用，但也留下一个容易误用的情境：目录里还看得见报告，有人便当作这次新数据的成果。应把命令状态与输入身份一起记录，失败后明确写“旧文件保留，未生成本次有效报告”。不能为了让自动化显示绿色，就忽略异常或把错误数值替换成零。

如果生成成功但独立核对失败，输出已存在，却不能交付为已核对结果。保留输入、报告和错误信息，调查口径或实现差异。不要让后面的发布动作无条件接着执行。这里的停止规则来自具体依赖：后一步需要前一步的有效产物。

## 脚本、批处理与调度有不同职责

脚本定义怎样做；调度决定何时做；模型在需要解释或处理新情况时参与。若只是每天同格式求和，不需要每天启动一个新模型重新设计统计方法。若输入规则经常变化，可以把异常留给人工或 Codex 判断，而不是给脚本无限的自动修复权限。

Codex CLI 当前还提供非交互 `exec`，可用于需要模型参与的批处理；本机只核对了 `codex exec --help`，没有运行新的模型任务。其参数、输出与运行边界见 [OpenAI 官方 CLI reference](https://learn.chatgpt.com/docs/cli/reference)。它会使用相应模型资源，不能与此处无模型调用的 Python 任务混为一谈。

真的需要定时运行时，先明确执行机器是否会开机、输入什么时候准备好、重复触发会怎样、输出谁会读取、失败通知给谁。避免两个任务同时写同一输出，必要时先用不同文件名保留每次结果。先手工运行通过，再按你选择的调度环境设置；本书不会因介绍自动化就自动开通或替你部署。

## 动手：交付一条能解释重复与失败的命令

在自己的副本选一个新输出位置，完成同输入两次运行、一个明确的输入扰动、一次坏输入失败。记录运行目录、命令、字节比较、数值变化和旧文件状态。让 Codex 解释其中哪些步骤需要判断，哪些已经可以交给确定性程序。

完成标准是后来的人能只运行同一入口复现结果，遇到失败知道该停止在哪里，且不会误把旧报告当作新成果。把重复工作固定下来之后，你才能把注意力留给真正变化的任务。
