# 第 9 章：项目约定与会话接续

昨天你和 Codex完成了状态筛选。今天换一个会话，它又问“怎么运行”，甚至准备重写已经可用的列表。旧聊天中不是没有答案，但答案散在多次讨论、失败尝试与过时计划里。接续的困难，不只是记忆不够，还包括不知道哪些状态仍然有效。

本章沿用第 8 章的 `my-tasktrail`。你将留下两份短文件，再用一个新会话验证它能否准确恢复工作。完成状态是：新会话知道当前目录、已有能力、真实检查、尚未完成的事项，并能提出合适的下一步，而不是从头重复实施。

## 稳定约定与当前状态各写什么

有些信息在许多任务中都成立，例如不引入第三方依赖、测试命令、样本不要当作写入练习。这类信息适合写进项目指引。另一些信息很快会变，例如筛选是否已实现、哪项测试刚失败、下一次先检查什么。这类信息适合放在接续记录。

Codex 支持 `AGENTS.md` 作为项目指引。2026-10-25 打开核对的[官方说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)指出：CLI 启动时构建指引链，项目发现通常从项目根目录走到当前工作目录，较深层内容在组合时覆盖前面的相应指引；同层存在 `AGENTS.override.md` 时会优先选择它。文件改后应重新启动核对，不能假定正在运行的会话自动重新加载。这里先用一个短文件，不需要为了练习去改变全局配置。

本书建议再用 `progress.md` 保存阶段状态。**这个名字和下面的格式是教材约定，不是 Codex 必须存在的特殊文件。**需要通过项目指引或当前任务明确要求读取。文件不会替你运行测试，也不会让一项失效结论永远正确；接续时仍要与代码和实际输出交叉检查。

## 给自己的副本补一份短指引

先确认当前打开的是**自己的 `my-tasktrail`**，不是教材根目录，也不是 `cases/B-tasktrail/starter`。用编辑器创建 `AGENTS.md`，或把下列内容发给当前有写入权限的 Codex，要求只在副本内保存：

```markdown
# TaskTrail 工作约定

- 离线 Python 标准库 CLI，不增加第三方依赖或在线服务。
- 入口 tasktrail.py；--data 指定数据路径，不把 sample.json 用作写入练习。
- 修改后运行 python3 -B -m unittest discover -s tests -v；Windows 用 py -3。
- 自动测试使用系统临时目录；手工新增任务使用自己的新数据文件。
- 继续前读 progress.md，并核对实际代码；交付写明命令、结果和未验证部分。
```

这些内容没有要求“所有任务先写完整规划”，因为小改动不需要那套流程。它也没有列出当前实现的全部函数，函数可能很快变化，重复的清单容易过时。短指引应保留能够减少反复纠正的事实，而不是把刚才每一句聊天都升级为永久规则。写下指引也不授予额外文件权限，实际可读写范围仍以当前环境为准。

如果工作副本位于教材 Git 仓库内，上层也可能有项目指引；启动位置与层级会影响读到的内容。让 Codex说明它实际加载或读取了哪些来源，再确认当前任务范围是这个副本。不要修改教材根目录的约定来“修复”一次学习任务。

## 把状态写到能够继续的位置

接着在同一个副本中创建 `progress.md`。下面是**格式示例，不是你的运行日志**。把状态和检查替换为真实结果；还没跑过就保留未验证：

```markdown
# TaskTrail 当前状态

目标：列表增加 --status open|done|all，默认仍显示全部。
位置：当前 my-tasktrail；入口 tasktrail.py，读写逻辑 tasks.py。
已做：按实际情况填写；不要把参考成品能力当作自己的成果。
检查：写明目录、Python 版本、实际命令、退出码与关键结果。
限制：没有多用户同步；筛选不能改数据格式或丢掉任务。
待做：写一项最有价值的下一步；未确认的行为直接写未确认。
```

一条真实记录可能是“在副本运行 `list --status open`，样本只显示编号 1；尚未检查数据字节是否保持不变”。它比“筛选完成、测试没问题”更有接续价值，因为新会话知道下一步缺什么证据。若你使用了教材参考成品，也写明来源，不能把复制当作自己的独立实现。

实现后的状态应与文件相符。假如记录说“已支持 `--count`”，帮助和代码却没有这个选项，接续时应把它标为冲突并调查，不能为了配合记录再编一段运行结果。代码、说明、聊天都可能过时，接续文件只是一个较短的入口。

## 新会话先恢复，再决定行动

保存文件后，结束当前会话。在操作系统终端进入 **`my-tasktrail`**，运行：

```sh
codex --sandbox read-only
```

Windows 继续用自己已确认的命令入口；App 或 IDE 用户在同一副本开启新聊天。首次恢复先用只读范围，目的是判断状态，不立即执行下一功能。向 **Codex 输入框**发送：

```text
请先读取当前目录的 AGENTS.md 与 progress.md，再查看必要代码。
本轮先不修改文件，不读取教材的 solution。
请用五句话恢复状态：目标、已有实现、实际验证、未验证项、下一步。
指出记录与文件之间是否有冲突，并引用支持关键结论的路径。
若准备继续添加 list --count，请只说明它的最小改动和验收，先不实施。
```

`--count` 在这里是下一项候选功能，当前参考成品没有实现它。这个具体但尚未开始的任务，能帮助你检查接续是否有效：它应沿已有列表与筛选关系考虑计数，而不是另造数据格式。若你只想恢复状态，不做后续功能，删去最后一句即可。

新会话引用了 `progress.md` 不等于恢复正确。检查它是否找到实际目录，是否误说筛选已经通过所有检查，是否把待做当作已做。你可以选择一条关键结论，让它引用相应实现或测试。若缺少上下文，补那一块；不用把前一会话数十屏内容全贴回来。

## 约定没有生效时怎样查

如果新会话完全没提指引，先确认文件确实叫 `AGENTS.md`，保存在当前副本；再查实际启动目录与是否存在更优先的同层 override。官方说明也提到指引存在读取大小限制。这个案例的短文件不需要调整限制，先排除路径与文件名，比扩大配置更直接。

若是当前旧会话没有自动遵循新文件，明确要求它读取并总结，再在新会话重新核对。不要只凭保存成功就宣布“自动加载验证通过”。本书制作已核对官方发现规则，并执行 TaskTrail 的 CLI 与单元测试；**没有替你实际完成跨会话协作**，这项能力要通过下面的练习观察。

如果指引越写越长，先问哪条规则对应真实反复发生的问题。将“这次筛选还有一个测试没跑”移到状态记录；删除已经失效的约束；保留启动、数据与验证这类仍然有用的内容。接续的目标是减少重复调查，不是让每个小任务背负全部项目历史。

## 动手练习：只靠仓库留下的入口继续

关掉旧聊天视图，只给新会话工作副本与上面的恢复任务。对照它的五句话，亲自确认一条已实现行为和一条尚未验证的边界。最后在 `progress.md` 补上一行：“本次接续实际发现了什么，下一项检查是什么。”若没有启动新会话，写“未进行接续验证”，不要勾选为已完成。

你留下的不是聊天备份，而是下一次行动的入口。遇到更大的项目，同样先保留目标、事实、证据与缺口，再让新会话从真实状态继续。
