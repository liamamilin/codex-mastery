# 第 26 章：什么时候值得使用多个 Agent

接手 TaskTrail 时，你想同时弄清入口、检查测试、审阅风险。多个 Agent 听起来很合适，但如果三个人一起修改 `tasks.py`，你可能得到三份各自合理、互相覆盖的答案。并行增加的是执行单元，协调问题不会自动消失。

本章训练分工判断。完成后，你应能选择一组可独立推进的任务，说明各自文件范围、返回证据与整合责任；也能在不值得时，明确选择单 Agent 顺序完成。

## 先看依赖，再看人数

两项工作只有在不需要等待彼此的中间结果时，才适合同时推进。调查 TaskTrail 的运行入口，与检查当前基础测试覆盖哪些输入，可以并行读取同一版本；实现新筛选之后的最终审阅，却需要等待实际改动，提前审阅只能检查旧版本。

你可以先让两个只读调查返回文件路径和不确定项，再由主 Agent 实施，完成后请其中一个检查变化。这比把“调查、实施、最终审阅”同时启动更符合依赖。并行的价值来自等待时间与认知工作能够拆开，不能靠多开几个窗口制造。

任务过小时，分工说明和汇总可能比实际修改还长。改一个明确文案、补一条已定位保存调用，通常没有必要拆成多 Agent。复杂问题也未必适合立即拆分：若大家还不清楚目标，先由一个 Agent 调查关键事实，往往更容易形成可分配的边界。

## 当前客户端怎样表达分工

2026-10-25 实际打开核对的[官方子 Agent 文档](https://learn.chatgpt.com/docs/agent-configuration/subagents)说明：本地 Codex 可按直接要求或适用项目/Skill 指引开展子 Agent 工作；App 与 IDE 显示活动，交互 CLI 可用 `/subagents` 查看线程。子 Agent 会额外消耗模型与工具资源，继承当前沙箱设置；文字要求“只读”并不自动创建另一套只读沙箱。

这里区分官方资料与本机验证：本书制作实际使用了四个 Agent 参与分工，并按文件范围整合；没有做单 Agent 对照计时，也没有证据支持固定倍数的提速。本章没有另行启动一套 CLI 交互来实测 `/subagents`。入口与账号支持有差异时，以当前客户端和官方说明为准，不需要为练习开通新付费服务。

在已有任务中，可以直接说明独立任务、等待关系和交付形式。下面是**教学分工任务**，按自己的目录改写后发给 Codex：

```text
请用两个子 Agent 只读调查 my-tasktrail 的同一当前版本。
甲：确认入口、数据路径与可运行命令，返回文件依据与未知条件。
乙：检查现有测试覆盖，指出一个值得补验的边界，不修改代码。
两者都不读取教材 solution，不安装依赖，不改写样本。
请等待两份结果，由主 Agent 对照文件消除冲突，
给出最小实施范围与验证办法，先不开始修改。
```

若当前环境不支持子 Agent，用一个 Agent 分两次完成同样调查即可。这项练习的终点是可靠的分工与证据，不是一定看到两个活动卡片。

## 写入任务需要更清楚的隔离

只读任务也可能基于不断变化的文件得到矛盾结论，因此调查期间尽量固定版本；必须写入时，边界更重要。可以让一个 Agent 只修改实现，另一个在独立位置准备样本与检查建议，主线控制最终落盘。不要让两者分别创建不同的数据格式，再期待自动拼合。

Git worktree 是一种隔离工作目录的办法。核对日的[官方 Worktrees 文档](https://learn.chatgpt.com/docs/environments/git-worktrees)要求项目属于 Git 仓库；App 新聊天可选择 Worktree 与起始分支。每份检出有独立文件，但隔离目录不等于接口天然一致，也不代表副本含有你期望的所有本地状态。

本章不要求你新建 worktree。已有环境可按官方入口选择已知起点；不熟悉时，独立练习副本与明确文件范围也能先练习。普通复制不会共享 Git 历史；两种方式都应核对实际路径、依赖和输入数据，不能把另一目录的测试结果当作本目录证明。

同目录按文件范围分工时，要明确交叉文件由谁负责。正文作者不修改全局配置，案例作者不重写主题，主线再统一接入，这是本书制作采用过的约束方式。它降低互相覆盖的机会，但主线仍需检查接口和构建；边界本身不是集成已经成功的证据。

## 返回结果要能被下一人使用

“调查完毕，没有问题”很难整合。更有用的返回包括实际查看的对象、关键结论、对应路径、执行结果与未验证条件。发现疑似缺陷时给一项能区分原因的检查，不要只列十种可能性。

主 Agent 不能只把三份总结粘贴到一起。两份报告冲突时，先核对是否读取同一版本、执行目录是否一致、哪个结论来自观察，哪个是推测。多数票不会把猜测变成事实。审阅者如果只看实施者的总结，也可能重复同一个错误假设；至少挑一条关键行为独立检查。

实现合并后还要针对整合产物验证。两个分支各自通过，不证明组合后的入口、测试导入和数据格式一致。发现覆盖冲突时，保留目标行为与双方证据，逐处解决，不直接以“后来的版本”为准全部替换。

## 有成本，才需要解释收益

多个 Agent 会重复获取部分上下文，主线也要花时间分配与整合。判断是否值得，可以比较三件实际事情：是否得到以前没有的独立观察；是否减少本来必须顺序等待的工作；整合时是否引入了额外错误。

不必虚构一张精确收益表。一次练习后写“两个调查并行完成，但入口调查只有几行，分工成本偏高”，也是有价值的结论。下一次可以保留测试审阅，其他工作由主 Agent 完成。

如果子任务迟迟没有产生证据，先询问当前对象、阻碍和已执行动作；目标变化时及时收回或调整任务。不要为了等待一个低价值分支，让所有可继续工作停住；但依赖其必要结论的实施也不能靠猜测越过。

## 动手练习：选择分工，或说明为什么不分

从自己的 TaskTrail、LinkShelf 或毕业题副本选一项真实工作。先用三句话描述依赖、文件边界和整合检查，再决定用一个还是多个 Agent。若选择并行，至少取得一份能独立核查的返回结果；若选择不并行，指出哪项依赖或协调成本使顺序工作更合适。
